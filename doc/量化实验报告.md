## 2. 实验一：秒杀高并发压测

### 2.1 方案

- **防超卖机制**：Redis Lua 预扣库存（原子）→ 乐观锁落库 → 一人一单约束 → 金额按秒杀价+运费计算。
- **实现类**：`SeckillConcurrencyTest`（`@SpringBootTest(RANDOM_PORT)`，真实 MySQL + Redis，自造压测商品与用户，幂等清理）。
- **三个档位**（CountDownLatch 同时放行）：
  1. 服务层 100 并发抢 50 库存（秒杀价 3.90 元，限购 1）
  2. 服务层 500 并发抢 200 库存（商品库存 199，放大档；带 `@EnabledIfSystemProperty(stress.test=true)`，不加参数不执行）
  3. HTTP 接口层 100 并发抢 50 库存（真实 Tomcat 随机端口 + JWT 鉴权 + Redis Token 校验链路）

### 2.2 数据（2026-10-17 复测，`mvnw test -Dtest=SeckillConcurrencyTest -Dstress.test=true`，3/3 通过）

| 档位 | 总请求 | 成功订单 | 售罄拒绝 | 系统错误 | 墙钟耗时 | QPS | 防超卖校验 |
|---|---|---|---|---|---|---|---|
| 服务层 100 并发 / 50 库存 | 100 | **50** | 50 | 0 | 698 ms | 143.27 | ✅ 零超卖 |
| 服务层 500 并发 / 180 库存 | 500 | **180** | 320 | 0 | 3 021 ms | **165.51** | ✅ 零超卖 |
| HTTP 层 100 并发 / 50 库存 | 100 | **50** | 50 | 0 | 1 695 ms | 59.00 | ✅ 零超卖 |

500 档补充指标：平均单请求耗时 2 280.7 ms，P95 2 965 ms。

**与上一版的差异必须如实说明**：上一版（2026-10-10，测于安全修复 `a493d18` 之前）同档位墙钟为 9 249 / 17 254 / 9 035 ms，QPS 10.81 / 28.98 / 11.07。本轮数值好了一个量级，但**不能当作"优化后性能提升"的结论**——本轮与上一版的差异至少有两个不可控来源：① 本机 MySQL 与操作系统的缓存冷热（本轮同一 JVM 内先跑了 100 档再跑 500 档，热态）；② 上一版测量时机器上并行跑着 AI 服务与向量索引重建，CPU 争用严重。本轮为单次测量、未做重复取中位，且测量期间另有网络型任务在跑（本地推理链路不受影响）。

**这一档实验真正要主张的是正确性而不是吞吐**：三档并发下成功订单数都精确等于库存、售罄拒绝全部返回业务码 50012、无一人一单被突破，这个结论与机器负载无关，因此可信且可复现。吞吐数字引用时应标注"本地热态单次测量"，如需严谨的性能结论，应按固定预热轮次 + 多次重复 + 独占机器重测。

历史对照（2026-10-10，环境含 CPU 争用，实现已变更）：

| 档位 | 墙钟耗时 | QPS | 防超卖校验 |
|---|---|---|---|
| 服务层 100 / 50 | 9 249 ms | 10.81 | ✅ |
| 服务层 500 / 180 | 17 254 ms | 28.98 | ✅ |
| HTTP 层 100 / 50 | 9 035 ms | 11.07 | ✅ |

### 2.3 一致性校验（每档全部通过）

- 成功订单数 **恰好等于** 秒杀库存（不多卖一单）；
- 未成功请求 **全部** 返回"已抢光"业务码（50012），无系统异常；
- Redis 剩余库存归零，DB 订单数 = 库存数，成功用户数 = 库存数（一人一单）；
- 订单金额 = 秒杀价 + 运费（与 `computeFreight` 同口径校验）。

### 2.4 分析

1. **正确性**：Redis 原子预扣 + 乐观锁组合下，库存扣减精确无误差，"一人一单"在高并发下无一例突破。
2. **扩展性**：并发从 100 提到 500，QPS 由 143.27 升至 165.51、墙钟仅从 698 ms 增至 3 021 ms——售罄拒绝走 Redis 预扣的快速失败路径（毫秒级，不落库），高并发下 320/500 的请求被快速拒绝，摊薄了墙钟时间。说明"把绝大多数无效请求挡在 Redis"的设计目标达成。
3. **瓶颈**：500 档平均单请求 2 280.7 ms、P95 2 965 ms，成功请求要走完"预扣 → 乐观锁落库 → 订单+明细插入"的全链路，排队发生在 10 连接的 HikariCP 池上。这是单实例默认配置的预期瓶颈，可论证方向：连接池扩容、库存扣减异步落库（Redis 对账）、水平扩展。HTTP 档 QPS 59.00 低于服务档 143.27，差额即真实 Tomcat + JWT 鉴权 + Redis Token 校验的开销（约为服务层的 41%）。

## 3. 实验二：意图识别准确率

### 3.1 方法与口径修正（重要）

**为什么必须换测试集**：原 103 题测试集在开发过程中被用于手工调试规则——`app/agent/intent.py` 里 `_HARD_HUMAN_WORDS` 的注释原文写着"在 103 题测试集上对其他意图零误伤"。规则照着这份数据调、又在这份数据上测，属于**数据泄漏**，得到的"规则通道 96.1% > 大模型 86.4%"是假结论（上一版报告因两次测量不同日而未暴露此问题）。

本轮处理：

- 新标 **hold-out 集 109 条**（`scripts/eval_data/intent_testset_holdout.json`，2026-10-17），标注过程未参与任何规则调参，作为**论文主口径**；原 103 题集降级为回归参考。
- 每条样本带 `feature` 标签：`lexical`（字面含业务词，规则理论上可命中）/ `semantic`（几乎无词面线索，只能靠语义理解），用于分通道×分特征交叉报告。
- 三通道消融，互不重叠：
  - `keyword`：纯规则（高置信前置 + 关键词兜底），零 LLM 调用；
  - `llm_only`：纯大模型（不做规则前置、不做兜底，调用失败即计错）；
  - `llm`：**生产路径** = 规则前置 → 大模型 → 关键词兜底。
- 另有 12 条**不计分能力探针**（多意图、上下文依赖、域外），用于诚实暴露边界（见 §3.4）。

**测量有效性保护**：Agnes 免费额度被打满时，生产路径会**静默回落关键词通道**，评测脚本会把"额度故障"当成"模型能力"。本轮第一次跑 `llm_only` 时 109 条里有 **77 条因 429 失败**，得到的"26.6% 准确率"是一份纯污染数据——当时是靠人工核对才发现的，随即把这条判定做成了脚本能力：统计 LLM 失败数与 429 次数，只要有最终失败就把结果文件加 `.INVALID` 后缀、写 `valid:false` 并以非零码退出，同时内置 429 长退避重试。此后所有 LLM 通道数据都由脚本自己把关（本轮最终存档 `llm_errors=0`、`rate_limited_calls=8` 全部被重试救回）。那份污染存档已就地改名为 `intent_eval_llm_only_holdout.20261017T1437.INVALID` 保留，作为"为什么要加这道保护"的证据。

**本轮自曝的一次同类错误（提示词泄漏）**：修完规则假阳性后复测，同一子集准确率从 93.3% 跳到 **100%**——原因是我在意图提示词里补的两条 few-shot 例句直接抄自 hold-out 原句（"派送员的电话能给我吗""能改成周末再送吗"）。这与"规则照着测试集调"是同一个方法学错误，只是发生在提示词层。已把这两条改成**不含任何测试集原句的抽象描述**后重测，仍为 100%（表 C），说明增益来自规则修复与模型本身，不是背答案。由此确立一条纪律：few-shot 例句不得取自任何被用于评测的样本。同时应注意 `_INTENT_PROMPT` 里原本就有若干引自旧 103 题集的例句，这是旧集上 LLM 分数偏高的另一个来源，而 hold-out 集不受该污染影响。

### 3.3 关键发现

1. **规则通道的 96.1% 是过拟合幻觉**：同一套规则在旧调参集上 96.12%、在 hold-out 全集上只有 **37.6%**，掉分 58.5 个百分点。分特征看结构更清楚：规则在"字面含业务词"的子集上 71.9%，在"只能靠语义"的子集上 **23.4%**——几乎等于随机落到 `faq` 兜底标签（`faq` 是默认返回值，这也是规则通道 faq 类"70% 召回"的虚高来源）。
2. **大模型的价值被精确量化了**：同日同 45 条子集上，含大模型的通道 **93.3%** vs 纯规则 **35.6%**；决定性的数字是 **semantic 子集 23.3% → 93.3%（+70 个百分点）**，lexical 子集也从 60.0% 提到 93.3%。真实用户问法正是"我上次买东西花了多少钱""有没有适合减脂期吃的粗粮""我不想跟机器说了，找个活人"这类**无词面线索**的表达——这就是本系统必须引入大模型的经验依据。
3. **规则前置层的价值不在准确率，而在成本、延迟与韧性**（三通道消融给出的修正结论）：本样本上"纯大模型"与"生产路径"总分相同（都 93.3%），规则前置并未提分，反而因"真人"这个词引入了 1 条假阳性。它真正换来的是：① 45 条里 4 条（8.9%）零成本短路，省 4 次 LLM 调用；② 寒暄类首 token 从"意图分类 + 生成"两次调用降为一次（实验四实测 smalltalk 首 token 2 256 ms，而上一版未做规则前置时测得 7 316 ms）；③ 额度/网络故障时链路退化到规则而不是中断服务——本轮 41 次调用里 **8 次触发 429，全部由退避重试救回**（`llm_errors=0`、`valid=true`），若彻底不可用则落到关键词兜底。
4. 因此规则层的正确定位是**高置信短路 + 故障兜底**，而不是语义分类器；写论文时应避免"规则与模型谁更准"这种比较，改用"分工 + 消融"的口径。同时给出一条具体改进：给"真人/人工"两个硬前置词补身份疑问排除（"是/还是"），或在意图提示词里加一条边界样例。
5. 剩余误判集中在 `logistics`（71.4%）：模型把"派送员的电话能给我吗""能改成周末再送吗"理解为诉求升级/政策咨询。这与实验六里导购未命中的 3 条一样，都属于**边界样例不足**，可通过 few-shot 直接改善，是论文"方案改进"小节的现成素材。
6. 论文建议的结论口径：*规则通道在人工调参集上可达 96.1%，但在未参与调参的 hold-out 集上仅 37.6%（无词面线索子集 23.4%），证明词表规则不能作为语义分类器；引入大模型后同一子集准确率提升至 93.3%（无词面线索子集 +70 个百分点）。规则前置层的贡献体现在调用成本（-8.9%）、首 token 延迟（寒暄类 7 316 → 2 256 ms）与额度故障下的服务连续性，而非准确率。*

### 3.4 能力边界（探针，不计分）

hold-out 集附 12 条探针，暴露三类当前架构无法正确处理的输入，论文应作为"局限性与改进方向"：

- **多意图**（3 条）：如"上次买的蜂蜜物流到哪了，另外再帮我推荐一款更甜的"。当时图是 argmax 单分支路由（`route_by_intent`），只会走一支——这是"工作流"而非"智能体"的直接证据。**本轮已由智能体改造解决大部分**：工具由模型自选、一步可并行多个，实测 3 条探针里 2 条同时取到两个诉求的资料，第三条把两个诉求都拿去检索了知识库（见 §8.6 与 §5.4），剩余风险是模型偶尔漏调，见 §10 第 14 条。
- **上下文依赖**（4 条）：如"有没有便宜点的""换一个牌子看看""这个适合送礼吗"。旧实现的语义召回与偏好抽取**只取最后一句话原文**，历史不进 query，因此这些问法会丢失上一轮品类。智能体改造已把最近 6 条历史交给规划器并明确要求补全指代（`AGENT_PLAN_SYSTEM_PROMPT` 规则 4），"这个适合送礼吗"这类带商详上下文的问法另有一条结构化通路（§8.3）；纯靠上一轮品类词接续（"有没有便宜点的"）仍未专测，改进项见 §11 第 7 条。
- **域外请求**（5 条）：进入导购分支后的实际表现由实验五定量测量（结论：闸门 0.35 会放行 60%）。

## 4. 实验三：RAG 检索命中率

### 4.1 方案

知识库扩容到 280 条后，原实验只覆盖 **36/280 = 13%** 的条目，"RAG 命中率"实际描述的是一个子集。本轮把评测分成两层，**分开报告、不混算**：

| 层 | 条目数 | 查询构造 | 难度 |
|---|---|---|---|
| `platform_faq` | 36（平台规则类） | 每条逐条**人工改写** 2 条同义问句，刻意避开原句词面 → 72 条 | 高，**论文主口径** |
| `product_kb` | 202（商品知识） | 模板构造：`X怎么储存比较好` / `X是哪里产的` → 404 条 | 低（商品名直接出现在查询里） |
| `category_kb` | 42（类目知识） | 模板构造：`你们X有多少种` / `X这一类有什么可以选的` → 84 条 | 低 |

覆盖率：280/280 = **100%**。三条召回通道：向量单路（bge-small-zh + Chroma 余弦）、关键词单路（`ai_faq.keywords` 子串计分）、双路合并（生产 `Retriever`）。指标 Hit@1 / Hit@3 / MRR，严格单一 gold。

### 4.2 数据（2026-10-17）

`platform_faq`（人工改写，72 条）：

|---|---|---|---|
| 向量单路 | 90.3% | **100%** | **0.949** |
| 关键词单路 | 47.2% | 79.2% | 0.626 |
| 双路合并（生产） | 90.3% | 98.6% | 0.943 |

`product_kb`（模板构造，404 条）与 `category_kb`（84 条）：

| 层 | 召回通道 | 查询数 | Hit@1 | Hit@3 | MRR |
|---|---|---|---|---|---|
| product_kb | 向量单路 | 404 | 100% | 100% | 1.000 |
| product_kb | 关键词单路 | 404 | 99.0% | 100% | 0.995 |
| product_kb | 双路合并（生产） | 404 | 100% | 100% | 1.000 |

### 4.3 分析

1. **向量通道是主力**：人工改写下 Hit@3 100%，对同义改写几乎全命中；纯关键词通道 Hit@1 仅 47.2%，证明语义检索的必要性（这条结论在扩容与规则改动后依然成立，与上一版一致）。
2. **双路合并略低于纯向量（MRR 0.943 vs 0.949）**：关键词通道在同义改写下贡献有限（改写刻意避开原词），保留它是对"用户原句直接命中"场景的兜底，工程上合理。
3. **商品域 100% 命中不能当能力证据**：模板查询里商品名整串出现，且商品名同时是 `keywords` 字段，词面与语义两路都必然命中。这一层的价值在于**证明扩容后的索引完整可用、没有因为条目数从 36 → 280 而出现召回退化**，不在于数值本身。
4. 唯一未命中样本（人工层）："订单多久不付款会自动失效" vs "订单支付有时间限制吗"——语义等价但措辞跨域较大。**改进方向**：为高频 FAQ 补同义问法库或多向量索引。

"有什么水果推荐""50 元以内有什么好物"正常返回带价格/产地/销量的三款推荐——即修复没有误伤正常导购。

### 5.3 归因与改进

- 延迟主体在**上游 LLM API**：本地链路（RAG 检索、会话记忆、SSE 转发、商品向量召回）合计 < 200 ms；三条分支的首 token 几乎与"串行 LLM 调用次数"成正比（1 次 2.3 s / 2 次 7.6 s / 3 次 19.2 s）。
- **必须诚实指出的问题**：导购分支首 token 均值 **19.2 s、最差 25.9 s**，是系统主打功能的真实体验。阶段提示（"正在为您挑选商品…"）在 5.3 s 就出现，能缓解焦虑但不能替代答案。演示时应优先走 FAQ 与寒暄分支，或先做下面的合并优化。
- **改进方向（按收益排序）**：
  1. **把偏好抽取合并进意图分类**——一次调用同时输出 `intent + keyword + maxPrice`，导购分支从 3 次降到 2 次，预期首 token 约 -6 s；
  2. **意图识别与商品向量召回并行**（召回不依赖抽取结果的那一路可先跑），再按需取用；
  3. 寒暄/高频短问句继续走关键词短路（已生效，实测 -5 s）；
  4. 意图分类换 fine-tuned BERT 分类头，从秒级压到毫秒级——这会同时改善全部分支。

### 5.4 智能体改造后复测（2026-10-17 19:20，同机同环境，17 问 × 1 轮，Java 8080 真实在跑）

工具编排改造改变了链路形状：不再有"意图分支"，每条业务问句都是**规划 1 次 + 作答 1 次**；
寒暄仍由规则前置直出（1 次）。新增加了一组 `multi_intent`（一句话两个诉求），
因为那正是旧架构答不全的场景，必须量一下它现在要花多少代价。

| 分组 | LLM 调用 | 样本 | 取证完成 | 首 token 均值 | 整轮均值 | 本轮商品卡 |
|---|---|---|---|---|---|---|
| smalltalk | 1（规则直出） | 4 | — | **3 241 ms** | 3 473 ms | 0 |
| faq | 2（规划 + 作答） | 6 | 6 082 ms | **9 648 ms** | 9 958 ms | 0 |
| recommend | 2 | 4 | 2 902 ms | **10 488 ms** | 12 022 ms | 6–8 |
| multi_intent | 2 | 3 | 6 788 ms | **10 950 ms** | 12 987 ms | 6–8 |

- **导购分支首 token 三轮对照**：19 240 ms（改造前，3 次串行 LLM）→ 11 133 ms（合并偏好抽取，2 次）
  → **10 488 ms**（智能体，2 次）。改造没有把主打功能拖慢，还略快了一点；
  取证阶段（工具跑完）在 2.9 s 就完成，卡片比文字先到位。
- **一句多诉求的代价与一次单诉求同级**（10 950 ms vs 10 488 ms），因为多个工具是在同一个规划步里

  本轮没有为此多花一次规划往返（会翻倍取证延迟），改进方向见 §11。
- 测量期间上游有排队（429 退避），`faq` 组内单条最大 15 396 ms；与 5.2/合并复测一样，
  绝对值受免费档服务质量影响，跨轮次只应比较"串行调用次数"这一结构量。

## 6. 实验五：反幻觉闸门（两道）

### 6.1 方案

系统有**两条语义完全不同的闸门**，上一版只测了第一条：

| 闸门 | 配置 | 失败后果 |

| 知识库闸门 `KB_SCORE_THRESHOLD` | 0.5 | 检索为空 → 生成节点输出**确定性拒答话术**（不经 LLM，零幻觉） |

### 6.3 结论与改进

1. **知识库闸门工作正常**：域内零误拒、域外 91.7% 拒答，且拒答路径不经 LLM、输出确定。
2. **导购闸门曾是真正的反幻觉缺口**：0.35 沿用搜索场景的值，导致 60% 的域外推荐请求被硬塞农产品，且结果荒谬到可读（手机壳 → 带壳毛豆，是"壳"字的语义近邻）。根因有三：① 阈值场景错位；② 导购分支**没有拒答出口**（候选为空还会降级到热销榜，等于必然给答案）；③ 意图分类把域外请求判成 recommend 之后，链路上再无人质疑。
3. **本轮已按曲线选点落地修复**（`app/config.py:REC_MIN_SCORE`、取数侧 `app/agent/executors.py:exec_product_search`、`app/prompts.py:build_rec_refusal_reply`；智能体改造前这段闸门在 `nodes.py:make_recommend_node`，改造后旧节点已删除，唯一实现在执行器里）：
   - 对话导购分支改用独立阈值 **0.47**，搜索框继续用 0.35（它有全文检索可退回，语义本来就不同）；
   - 新增**确定性拒答出口**：语义无强命中 + 品类词 LIKE 无命中 + 模型判定不属于经营范围时，
     直接输出导购拒答话术，**不经 LLM、不降级热销榜**；
   - 保留两条安全阀：LIKE 命中即推荐（"库里确实在卖"是正面证据，优先于模型的域判断，宁可少拒不误伤）；
     没有拿到判定（LLM 故障走兜底）时不拒答，故障期行为与改动前完全一致。
   - 复测（16:14 存档 `rec_gate.chat_lane_*`）：**域外泄漏率 60% → 0%，域内召回率 100% → 90%**；
     那 10% 的弱命中域内请求（如"30 块钱左右能买到什么坚果"，0.415）由品类词 LIKE 接住，
     端到端实测正常出推荐。
4. 新增的 `inDomain` 判定与意图分类、偏好抽取合并在**同一次 LLM 调用**里完成（见实验四），
   因此修复没有增加任何调用成本，反而少了一次往返。
5. 知识库闸门的余量需要随扩容复测：12 条域外问题 top-1 最大已达 0.596（阈值 0.5，余量 -0.096），
   建议在 `eval_refusal.py` 输出的分布上重选阈值，而不是固定沿用 0.5。

## 7. 实验六：智能导购召回与个性化（新增）

### 7.1 方案

- 标注集：40 条人工导购问句，覆盖全部主营类目；每条标注**可接受的二级类目集合** + 可选价格上限（单一 gold 集合，同类目内任意商品均计命中，跨类目的合理替代不计分）。
- 在售商品池 202 件，三条召回通道在同一池上对比：
  - `hot`：热销榜（无查询通道，对应线上第三级兜底）；
  - `keyword`：品类词 LIKE 商品名/副标题（线上第二级降级路径）；
  - `vector`：真实 bge-small-zh + `Chroma(product)` 语义召回（线上第一级）。
- 指标：Hit@1 / Hit@5 / P@5 / MRR / 类目覆盖率。
- 个性化：对照重放实验（见 7.4 的性质说明）。

### 7.2 数据（2026-10-17，commit 6a7cf8f）

| 通道 | 查询数 | Hit@1 | Hit@5 | P@5 | MRR | 类目覆盖 |
|---|---|---|---|---|---|---|
| 热销榜 `hot` | 40 | 7.5% | 15.0% | 5.0% | 0.101 | 10/40 |
| 关键词 `keyword` | 40 | 60.0% | 75.0% | 26.5% | 0.667 | 36 |
| **语义向量 `vector`** | 40 | **77.5%** | **92.5%** | **52.0%** | **0.842** | **40** |

### 7.3 分析

1. **语义召回相对关键词通道的增益是可归因的**：Hit@1 60.0% → 77.5%，P@5 26.5% → 52.0%。差距主要来自"用户说场景不说品类"的问法——关键词通道要求先抽出品类词再 LIKE，而"过年走亲戚拎点什么体面""给小宝宝做辅食买什么"这类问句抽不出词面匹配。
2. **类目覆盖率 40/40**：语义通道对每一个类目的问句都能召回同类目候选，说明 202 件商品构成的索引不存在类目盲区；热销榜只覆盖 10 个类目，因为它与查询无关。
3. 剩余 3 条未命中样本："浆果都有什么""给小宝宝做辅食买什么""有什么泡水喝的"——共同特征是**期望跨多个二级类目的聚合召回**，而向量通道按整体相似度排序、没有做类目多样化（MMR/分组召回）。改进方向明确：候选打散或按类目配额。

### 7.4 个性化对照重放（性质：机制验证，非效果评估）

方法：对每条问句取语义召回 top-8，选出"确实相关但排在第 4~8 名"（即纯语义错过 top-5）的商品作为目标；**合成**一个近期连购 3 件该商品同类目的用户历史；同一份候选分别经"无偏好（基线）/有偏好（个性化）"重排，比较目标商品进入 top-5 的比例与名次变化。重排函数与线上完全同一个实现（`rag/personalize.score_products`，三条链路共用）。

| 通道 | 目标商品进 top-5 | 平均名次提升 |
|---|---|---|
| 纯语义（无历史） | 0.0%（**构造使然**） | — |
| 语义 + 类目偏好重排 | 95.0% | +2.15 名 |

> **必须如实标注**：基线 0.0% 是因为目标商品就是按"基线落在 top-5 之外"筛出来的；判定所用的类目又正是被优化的信号本身。**这是一次机制验证**（证明重排公式能把偏好类目商品推入前五），**不是效果评估**——它不能证明个性化对用户有价值。真正的效果口径需要 A/B 或线上点击率，本系统未采集。`recommend_eval.json` 的 `personalization_replay.nature` 字段已写入这段说明，避免引用时丢上下文。

### 7.5 与首页 feed 的关系

同一套打分函数服务于三个入口（首页 feed、搜索框语义召回、对话导购），入口差异只体现在"有没有语义分"：首页无语义查询，语义项恒为 0，其余四项与权重完全一致。因此"同一件商品换个入口换个名次"的问题在架构上被排除，可解释理由标签（`AiRecommendController.buildReason`）取的正是这套分项的原始信号，展示口径与服务端打分同源。

其中**零评价商品的先验好评率参与排序，但不参与对外理由**：`signals.rate_conf` 标记口碑是实测还是先验，先验值不允许输出"好评率高"。

## 8. 实验七：智能体工具编排（本轮新增）

### 8.1 方案与口径

改造内容：把 6 个能力注册成 function schema（`app/agent/tool_defs.py`），用
`llm.bind_tools()` 让大模型自己决定**调用哪些工具**（`app/agent/nodes.py:make_agent_node`），
取代原来的"意图 argmax → 固定单分支 → 调一个工具"。

- **判分口径**：hold-out 集每条已标意图，映射到期望工具——
  `faq→kb_search`、`recommend→product_search`、`order→order_query`、`logistics→logistics_query`、
  `after_sales→after_sales_query`、`human→escalate_human`、`smalltalk→不调用任何工具`。
  命中定义是"期望工具在实调集合里"（允许并行多调），规则前置短路的 human/smalltalk 也算命中
  （它们本来就不该进智能体，把省掉的那次调用记成错误等于惩罚优化）。
- **工具执行用桩**（`eval_agent.py:StubJavaApi`），检索/商品向量召回/LLM 全部真实。
  原因不是省事：Java 不启动时所有业务工具都返回连接失败，`status=error` 会误触发反思重试分支，
  延迟与调用数都不再反映模型行为。**测的是"选什么工具"，不是"取数对不对"**；
  后者由 Java 侧单测与 §8.6 的端到端复核负责。
- 脚本：`scripts/eval_agent.py`（`--mode plan` 只跑到取证；`--mode full` 含作答）。
  沿用实验二的额度故障保护：只要有一次 LLM 调用最终失败就 `.INVALID` 并非零退出。

### 8.2 数据（hold-out 全集 109 条，两次独立测量）

| 存档 | 时间 | 工具选择准确率 | lexical / semantic | 规划调用 | 取证延迟 均值 / P50 / P95 / 最大 |
|---|---|---|---|---|---|
| `agent_eval_plan_holdout_prefix.json` | 18:51 | **94/109 = 86.2%** | 96.9% / 81.8% | 105 | 7 714 / 2 131 / 28 159 / 68 148 ms |
| `agent_eval_plan_holdout.json` | 19:35 | **94/109 = 86.2%** | 93.8% / 83.1% | 121 | 7 529 / 2 249 / 27 850 / 32 423 ms |

两次之间唯一的差异是规划提示词补了"寒暄/无事实需求不要调用工具"（§8.3 缺陷一）。
**总体分完全相同（94/109），不该解读成"修订无效"，也不该解读成"修订无代价"**：
n=109 时 1 条 = 0.9 个百分点，分意图每类只有 14~20 条，2~3 条的涨跌都在噪声内。
能站住的读法是结构性的那两条：

- 修订的方向对：smalltalk（期望"不调用任何工具"）**8/14 → 11/14（57.1% → 78.6%）**，
  超调的 `kb_search` 从 13 次降到 9 次；代价是 human/faq/logistics 各掉 1~2 条。
- 修订后的**干净**复测不能拿 hold-out 报（观测→改→同集复测就是泄漏），
  改用零重合新集，见 §8.3。

主口径取 **86.2%（n=109，两次独立测量同分）**，并明确它的性质：
这是"模型自选工具"的能力测量，Java 用桩，测的不是回答正确性（§8.1 已声明口径）。

分意图（以 19:35 那次为准）：

| 意图 | 期望工具 | 样本 | 命中 | 命中率 |
|---|---|---|---|---|
| recommend | product_search | 16 | 16 | 100.0% |
| after_sales | after_sales_query | 15 | 14 | 93.3% |
| faq | kb_search | 20 | 17 | 85.0% |
| order | order_query | 15 | 13 | 86.7% |
| human | escalate_human | 14 | 12 | 85.7%（另有规则直出） |
| smalltalk | （不应调用） | 14 | 11 | 78.6% |
| logistics | logistics_query | 15 | 11 | 73.3% |

**最有论文价值的是这一组对照**：同一批 hold-out 题、同一套标注，
规则通道在语义子集上只有 **23.4%**（全集 37.6%，见 §3.2），
而把选择权交给 function calling 后 semantic 子集 **83.1%**、全集 86.2%。
这把实验二那句"规则不能当语义分类器"从批评变成了替换证据——不是把规则改得更聪明，
而是换了一层能读懂句子的决策者。规则层则退到它真正擅长的位置：human 强诉求与纯寒暄的高置信短路。

logistics 仍是最弱一类（73.3%），且误判方向很有意思："什么时候上门取件"→`after_sales_query`、
"那单从哪个城市发出来"→`order_query`、"能改成周末再送吗"→`order_query`。
这三条与其说选错，不如说**派送环节的事实确实分散在订单/物流/售后三个接口里**，
模型选了"最近的那一个"。旧架构按 argmax 也只能挑一个，差别是它挑完就再也不看别的分支。

### 8.3 缺陷一与缺陷二：寒暄被硬塞工具、商详指代被语义召回抢走卡片

**缺陷一：寒暄被硬塞工具（smalltalk 57.1%）**。14 条纯寒暄里 6 条被调了 `kb_search`，
"今天可真热啊""嗯嗯，晓得了"这类句子明明没有需要核实的事实。根因在规划提示词：
它只写了"任何需要事实支撑的内容都必须调用工具"，没写反过来的"没有问题就不要取证"。
修订：`AGENT_PLAN_SYSTEM_PROMPT` 增加规则 2（纯寒暄/礼貌回应/安抚一律不调用工具，
并说明为什么——既烧额度又把无关资料塞进回复）。

**修订后的干净复测**：修订依据来自 hold-out 上的观测，再拿 hold-out 报"修订后准确率"就是二次泄漏。
因此新写一份**未参与任何调试**的定向探针集 `scripts/eval_data/agent_probe_overcall.json`
（12 条寒暄 + 8 条业务对照，句子全部新造，与 hold-out 零重合）：
**总体 18/20 = 90.0%，smalltalk 不调用工具 10/12 = 83.3%**（修订前 hold-out 同口径 57.1%）。
剩余 2 条是收尾语（"先这样吧，我看看别的""嗯嗯，晓得了"）——注意本评测**每条都是冷启动单轮、
不带对话历史**，真实会话里这类句子前面有内容，模型去补调订单/售后并不算错，
所以这个 83.3% 是对"无上下文"情形的保守下界。
⚠ 引用时要分开：hold-out 的 smalltalk 类自本次修订起不再是无泄漏口径，后续复测只能作"行为回归"用。

**缺陷二：商详页指代句的卡片被语义召回抢走（E2E 实测，非统计缺陷）**。
从商详页进线问"这个能放多久？怎么保存"，回复内容正确（用了商品事实），
但气泡下面一次冒出 8 张卡、首张是金针菇。查了分数才确认问题不在阈值：

| 问句 | top-1 分 | 过 0.47 闸闸门条数 |
|---|---|---|
| 这个能放多久？怎么保存 | 0.518 | 8 |
| 它新鲜吗 | 0.526 | 8 |
| 这款甜不甜 | 0.573 | 8 |
| 哪种茶叶比较好（真品类问句） | 0.558 | 8 |

指代句与真品类问句的向量分布**完全重叠**，调阈值救不了。修订把判据换成结构性的：
`exec_product_search` 新增第 ⓪ 级——有 `productId` 且模型没给 `keyword` ⇒ 问的就是眼前这件，
只出这一张卡；同时品类词 LIKE 命中 ≥2 条时优先采信 LIKE（不再让语义召回混进无关品），
并在 `_ok()` 出口统一按 `REC_CARD_LIMIT=4` 截断且让 payload 与卡片同源。
回归：`test_browsing_product_beats_strong_semantic_recall`（用强命中假索引复现当时分数）、
`test_keyword_with_enough_like_hits_skips_semantic_lane`、`test_card_list_is_capped`、
`test_named_category_while_browsing_is_not_hijacked_by_product_qa`（反向保护，点名别的品类不被指代分支抢走）。

### 8.4 缺陷三：`inDomain` 是可选参数，域外请求因此绕过拒答出口（hold-out 探针实测 1/5 泄漏 → 已修）

19:35 那次跑的域外探针里，「帮我写一首关于秋天的诗」拿到了 **1 张商品卡**（`product_search` 返回 ok）。
根因不在闸门，而在**调用契约**：`inDomain` 在 schema 里不是必填，模型经常不写它；
而执行器有一条刻意保守的规则——"没有拿到经营域判定时一律不拒答"（A 轮为了避免把反幻觉做成新故障源）。
两条合起来的效果是：**模型省略 = 放弃拒答 = 落到热销兜底并出卡片**。旧架构里 `inDomain` 由
意图那次调用必出，所以没有这个洞；换成 function calling 后它变成了"模型想不想填"。

修复：`tool_defs.py` 把 `inDomain` 提为 `required`，描述里明确"必须给出判断，省略等于放弃拒答的机会"。

复测（全部真实模型，Java 用桩）：

| 集 | n | 域外拿到卡片的条数 | 说明 |
|---|---|---|---|
| 新写域外集 `agent_probe_ood.json`（与 hold-out 探针零重合） | 8 | **0/8** | 2 条被调 `product_search` 且 `status=refused`，6 条模型直接不选导购工具 |
| hold-out 域外探针（曾观测过 1 条泄漏，只作回归） | 5 | **0/5** | 泄漏那条「帮我写一首关于秋天的诗」现在不调用任何工具 |
| 域内泛推荐保护集（无品类词/品类宽） | 6 | 6/6 正常出 4 张卡 | 确认必填字段**没有**把正常导购误拒 |

域外那 6/8"压根不调 `product_search`"是好事也是口径问题：它省掉了一次取数，但回复改由
"本轮没有资料"的引导分支生成（提示词要求不编造业务信息），不再是那句确定性拒答话术。
论文里应写成"域外请求 0 卡片泄漏"，不要写成"0 泄漏且都走了确定性拒答"。

### 8.5 有界性与降级路径（结构保证，单测覆盖）

工具编排把决策权交给模型，就必须把"最坏情况"写死在代码里，不能指望提示词自觉：

| 机制 | 实现 | 保证 | 回归测试 |
|---|---|---|---|
| 步数上限 | `AGENT_MAX_STEPS=2` | 单轮最多 2 次规划往返 | `test_loop_is_bounded_by_max_steps` |
| 调用数上限 | `AGENT_MAX_TOOL_CALLS=4` | 一步内再多也只执行前 4 个 | `test_tool_calls_capped_per_turn` |
| (工具, 参数) 去重 | `seen` 集合 + `already_called` 回灌 | 重复调用不重复取数、不重复烧额度 | `test_duplicate_tool_call_is_skipped_not_reexecuted` |
| 提前退出 | 本步资料全部可用即停 | 资料够了不再多问一次模型（省 6~15 s） | `test_loop_exits_early_when_material_is_already_usable` |
| 反思重试 | 出现 empty/error 才再规划一步 | 空结果可改写检索表述重来一次 | `test_reflection_rewrites_query_after_empty_result` |
| 能力协商 | `_resolve_planner` 捕获 `NotImplementedError` | 上游不支持 function calling 时退回"分类 + 单工具"，功能不回退且打 WARNING | `test_degraded_path_still_uses_one_tool` |
| 规划故障 | 规划调用抛异常 → 降级单工具 | 429/超时期间仍能取证作答，不白屏 | 同上（`plan_error` 参数化） |
| 闸门不可绕过 | 把关全在 `executors.py` | 域外拒答/未登录/检索为空等出口与调用者无关 | `test_out_of_domain_recommendation_refuses_without_llm` 等 |

改造后**旧的 5 个业务节点与重复的一份降级阶梯被整体删除**（`faq_retrieve`/`order_query`/
`logistics_query`/`after_sales_query`/`recommend_query` 节点、`tool_type`/`tool_result`/`faq_context`
状态字段），图里只剩 `intent →（smalltalk | human_fallback | agent → generate）`。
理由：同一套闸门留两份实现必然漂开，而多工具一轮取证本来也没有"单一 tool_type"可言。
`observations[]` 成为唯一的"本轮取到了什么"表示，SSE 的 `status{stage:agent, tools:[…]}` 直接暴露它。

### 8.6 端到端复核（真实 Java + 真实索引 + 真实模型，19:30 前后）

| 输入 | 工具 | 卡片 | 结果 |
|---|---|---|---|
| 商详页进线「这个能放多久？怎么保存」 | product_search | 1 张（就是这件赣南脐橙） | 按商品事实答"常温避光、保质期 30 天"，没有编造 |
| 商详页进线「有没有比这个便宜的橙子」 | product_search | 4 张 | 正确挑出更便宜的一款并给出差价；同时如实说明"那是椰子不是橙子" |

两个诉求、2 次 LLM 调用、一次答完——这是旧单分支架构做不到的。

### 8.7 口碑与销售数字的表述边界（E2E 三轮实测越界 → 口碑一句已服务端模板化收口）

商品事实里 `reviewCount=3`、`positiveRate=66.67`、`topKeywords=[新鲜,均匀,回购,多汁,好]`、`sales=1046`。
对同一件"赣南脐橙"连续三轮真实端到端回复，观察到三类语义越界：

| 轮次 | 模型原话 | 问题 |
|---|---|---|
| 1 | "好评里也多次提到'多汁、好'，**口碑不错**" | 66.67% + 3 条评价不足以支撑"不错"这个结论 |
| 2 | "**买家回购率**也说不错" | `回购` 只是评价文本里提取的词，不是一个率 |
| 3 | "1046人**回购**" | `sales` 是销量，不是回购人数 |

已做：`AGENT_ANSWER_SYSTEM_TEMPLATE` 规则 3 补三条硬约束——引用口碑必须把数值本身说给用户、
topKeywords 是词不是指标、sales 是销量不得说成回购/好评人数，并明确把"口碑不错/好评率高/很受欢迎"
列为禁句；三条各加断言（`test_answer_prompt_forbids_praise_in_place_of_numbers`）。
复测后禁句未再出现，但第 3 轮冒出了新的换说法（"1046人回购"）。

**必须如实写进论文的边界**：提示词层的约束能压住具体禁句，压不住同义改写；
**数值级编造**（凭空给出好评率、价格、产地）在全部实测中未出现——这是闸门与"照抄字段"保证住的硬边界；
**语义级越界**（把一个真实数字安上错误的指标名）靠提示词只能降低概率。

**2026-10-18 已按确定性做法收口（改进项 #22 结案）**：口碑那一句改由服务端模板拼装——
`ai-service/app/tools/java_api.py:reputation_text()` 按 `reviewCount/positiveRate/topKeywords`
产出"3 条买家评价，好评率 66.7%，买家提到：新鲜、多汁"，零评价/字段缺失/脏字段（`"abc"`、`"无"`）
一律输出"暂无评价数据"；句子写进商品卡 `reputation` 字段、与商详页 `format_product_facts` 同源下发，
作答提示词只允许**一字不改地引用**这一句（提示词侧的三条禁令同时保留，作第二道约束）。
思路是**把没有依据的话变成拼不出来的话**，而不是指望模型自律。

复测（真实模型，同一件赣南脐橙）：回复逐字复述"3 条买家评价，好评率 66.7%，买家提到：新鲜、均匀、回购"，
销量说成"已售出 1042 件"而非回购人数；同批三款零评价商品全部输出"暂无评价数据"，无一处好评率或回购结论。
`tests/test_reputation_text.py` 8 条钉住分支，并断言模板句内不得出现"不错/很高/受欢迎/回购率"这类结论词、
卡片与 payload 必须同源。

**这条结论的适用面仍要限定**：被模板绑住的只有"口碑那一句"。模型自己组织的其余话术（如"特别适合送礼"）
依旧是生成物，属于概率性输出。因此论文与答辩的口径只能是"**口碑宣称已模板化，数值与指标名同源**"，
不能写成"已杜绝虚假宣传"。

## 10. 局限性说明

1. 支付与物流为模拟实现，不影响本报告六个实验的度量对象。
2. 单机单实例的绝对吞吐不代表生产水平，正确性结论不受影响。
3. LLM 相关指标（实验二延迟、实验四）受 Agnes 免费档服务质量波动影响，复测数值会浮动；通道间的相对结论稳定。脚本已能识别额度故障并拒绝出数（见 §3.1）。
4. **实验二的两个大模型通道是 n=45 随机子集（seed=20261017），不是 109 条全集**——免费额度按窗口配额，串行跑全集会在中途被 429 打断。子集内 1 条样本 = 2.2 个百分点，因此"93.3% vs 93.3%"这种同分差异不应解读；可信的是与 35.6% 之间约 58 个百分点的量级差。补测全集的命令见 §9（去掉 `--limit` 即可，产物不会覆盖子集存档）。
5. **实验四为 1 轮 × 14 问的单次测量**，n=4 的分组 P95 无统计意义（表中改报均值与区间）；且测量与实验二共用同一额度窗口，上游排队会影响绝对值。
6. **实验一为单次测量、未做多轮取中位**，与 2026-10-10 那版数值差一个量级，差异来自缓存冷热与当时并行的 AI 服务/CPU 争用，不作为性能提升结论（详见 §2.2）。
7. `eval_results/` 里 `intent_eval_keyword.json`（2026-10-10）与 `intent_eval_llm.json`（2026-10-05）两份是旧集存档、且没有 `measured_at`/`git_commit` 字段——**无时间戳即视为未与本轮同源**，引用时必须以带 provenance 的文件为准。
8. 实验三的 `product_kb` / `category_kb` 两层由模板构造查询，难度低于人工改写，只用作"扩容后索引完整可用"的覆盖率证据。
9. 实验六的相关性判定是人工标注的**单一 gold 类目集合**，同类目内任意商品算命中，但跨类目的合理替代（如问榴莲返回同属热带水果的芒果）不计分——该口径偏保守，会低估实际可用性。
10. 实验六第 7.4 节是**机制验证**（合成行为），不是效果评估；个性化的线上效果未经 A/B。
11. 意图测试集仍存在"同一人标注 + 同一人写规则"的方法学局限；hold-out 集只解决了"规则照着它调"这一条，标注者一致性（双人 Kappa）未做。
12. 实验五的域外/域内导购探针各 10 条，样本量小，泄漏率与召回率的置信区间宽；结论应表述为"0.35 明显偏松、0.47 附近出现拐点"这一量级判断。
13. 秒杀实验的 QPS 受本机连接池与 CPU 限制，重点在防超卖正确性而非吞吐上限。
14. **实验七的判分口径是"期望工具是否被调用"，不是"回答是否正确"**：Java 用桩替换，业务工具必然返回成功，
    因此这里测的是规划层选择能力。副作用是多诉求覆盖没有硬保证——3 条 multi_intent 探针里 1 条只调了一个工具
    （少答一半），代码层面无法在不多花一次规划往返（+6~15 s）的前提下杜绝；论文表述应为
    "支持一句多诉求并行取证（实测 2/3 探针命中两个工具）"，不能写成"已保证"。
15. **实验七 n=109 是 cold-start 单轮、无对话历史**，且探针集每条独立成会话：上下文依赖类（"有没有便宜的"、
    "这个适合送礼吗"）本来就无解，脚本只记录行为不计分；这类能力要靠 §11 第 7 条的查询改写。
16. **实验七的延迟是长尾分布**（P50 2.1 s vs 均值 7.7 s、最大 68 s）：免费档上游排队主导绝对值。
    引用时应同时给出 P50 与"调用次数"这一结构量，不要只报均值。
17. **hold-out 集的 smalltalk 类与 5 条域外探针自本次修订起不再是无泄漏口径**（修订依据来自这两类在 hold-out 上的观测）。收益一律引用零重合新集：寒暄 `agent_probe_overcall.json`（n=20）、域外 `agent_probe_ood.json`（n=8）；hold-out 上重跑的同名分类只作行为回归。
    因此"修订后成绩"引用的是零重合新集 `agent_probe_overcall.json`（n=20）；
    hold-out 上后续跑出的数字只能作为行为回归，不能与 §8.2 的 86.2% 直接比高低。
18. 智能体的能力上限受上游 function calling 质量约束：本轮实测 Agnes `agnes-2.5-flash` 支持并行 tool_calls
    （`eval_agent.py` 与 §5.4 端到端均为真实调用），但换型号/换网关若不支持，`_resolve_planner` 会打 WARNING
    并退回"分类 + 单工具"。演示与答辩前必须确认日志里没有这条 WARNING，否则跑的是降级路径。
