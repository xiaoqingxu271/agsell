## 1. 模块概述

### 1.1 背景

需求文档将「限时特惠」列为 P1 功能，当前项目三端均未实现。本模块补齐该能力，并顺势做成**具备高并发设计深度的秒杀子功能**，作为毕设答辩的核心亮点。

### 1.2 目标



| 端    | 能力                                    |
| ---- | ------------------------------------- |
| 管理端  | 秒杀活动建档 / 编辑 / 上下架 / 删除，关联商品与秒杀库存      |
| 小程序端 | 首页「限时特惠」入口、秒杀列表（倒计时 / 库存进度）、秒杀详情与抢购下单 |
| 后端   | 高并发防超卖、一人一单、超时释放名额，复用现有订单 / 支付链路      |

### 1.3 答辩亮点（一句话总结）

**三层防超卖 + 双层一人一单 + 超时释放闭环**：Redis Lua 原子预扣拦截抢购峰值 → DB 乐观锁兜底扣减 → 数据库唯一索引兜底重复；订单超时自动取消时名额回补，全链路可量化、可并发压测演示。

## 2. 现状与约束（探查结论）

以下为代码现状，秒杀设计必须对齐：



1. **下单不扣库存，支付才扣**：`OrderServiceImpl.createOrder` 仅在创建订单时校验库存快照（快速失败）；`PaymentServiceImpl.createPayment` 支付成功时用乐观锁扣减（`stock >= quantity` 原子 UPDATE，防超卖）。秒杀必须沿用此模型，避免破坏普通订单链路。

2. **订单超时取消**：`OrderTimeoutScheduler` 每 60s 扫描，调用 `OrderServiceImpl.cancelExpiredOrders` 批量置为已取消（单条原子 UPDATE + 状态守卫）。秒杀订单被取消后需**回补 Redis 名额**，需在取消处挂钩子。

3. **Redis 已就绪**：`spring-boot-starter-data-redis` 已引入并配置（`application.yaml` `spring.data.redis`），当前仅用于 token。秒杀无需新增依赖。

4. **表结构**：`product`（stock/sales）、`product_spec`（stock）、`order`（`uk_order_no`、`idx_status_create_time`）、`order_item`（含 `spec_id` 供支付时扣规格库存）。

5. **管理端路由 / 侧边栏**：`/admin/{dashboard,users,categories,products,orders,reviews,after-sales,banners,traceability}`；秒杀管理追加在「产地溯源」之后。

6. **小程序首页**：`pages/index/index.vue` 现无限时特惠入口，需新增。

7. **错误码枚举**：`ErrorCode.java` 需新增秒杀专用错误码（见 6.5）。

## 3. 技术选型与量化对比

### 3.1 防超卖方案：Redis 预扣 vs 纯 DB 乐观锁



| 维度     | 纯 DB 乐观锁（直接下单）                          | **Redis 原子预扣（本方案）**                          |
| ------ | --------------------------------------- | -------------------------------------------- |
| 峰值 QPS | 单行热点下约 **2\~5k**（InnoDB 行锁 + binlog 开销） | 单实例 **10 万级**（内存 DECR，官方 benchmark \~110k/s） |
| 抢购瓶颈   | 数据库行锁（所有请求串行等同一行）                       | 内存原子操作（毫秒级）                                  |
| 超卖风险   | 需 `stock >= quantity` 条件 UPDATE，可防      | Lua 原子 DECR 判负，可防                            |
| DB 压力  | 峰值全部打到 MySQL                            | 99% 请求在 Redis 层终结，MySQL 只收尾                  |
| 复杂度    | 低                                       | 中（需缓存预热 + 释放补偿）                              |
| 宕机风险   | 无额外依赖                                   | Redis 宕机 → 需降级（活动直接走 DB 乐观锁）                 |

**结论**：毕设演示与答辩场景，Redis 预扣方案收益明确（能讲清 "高并发如何扛"），内存成本可忽略（每活动 3 个 key 约 200\~300B + 活动快照约 1KB，100 个活动 < 200KB）。采用 **Redis Lua 原子预扣 + DB 乐观锁兜底** 双保险。

### 3.2 是否引入 MQ 削峰



| 方案          | 收益        | 成本                                       |
| ----------- | --------- | ---------------------------------------- |
| 同步下单（本方案）   | 逻辑简单、演示稳定 | 下单事务 10\~20ms，单机 Tomcat 可支撑 1000 QPS 级演示 |
| RabbitMQ 削峰 | 极端峰值吞吐更高  | 需新增容器 / 配置 / 可靠投递与死信处理，工作量 +2 天，演示环境脆弱   |

**结论**：本期**不引入 MQ**。答辩时作为扩展点口述："生产环境可加 MQ 将下单请求异步化削峰"，避免把演示复杂度堆高。

### 3.3 一人一单：双层方案



| 层        | 手段                                                                    | 作用                   |
| -------- | --------------------------------------------------------------------- | -------------------- |
| Redis 预检 | `SETNX seckill:user:{id}:{userId}`（Lua 内完成）                           | 毫秒级拦截 99% 重复请求       |
| DB 兜底    | `order` 表 `UNIQUE KEY uk_user_seckill (user_id, seckill_activity_id)` | 持久可靠，防并发穿透与 Redis 异常 |

**关键设计**：MySQL 唯一索引对 `NULL` 值不参与冲突校验 —— 普通订单 `seckill_activity_id = NULL` 完全不受影响，秒杀订单天然一人一单，零侵入普通链路。

## 4. 总体架构与流程



```
管理端 SeckillListView ──► AdminSeckillController ──► AdminSeckillService ──► seckill\_activity 表

&#x20;                                                             │ 启动/变更时写缓存

&#x20;                                                             │ ① 活动校验(Redis快照)

&#x20;                                                             │ ② Lua 原子扣减(库存+防重)

&#x20;                                                             │ ③ 创建待付款秒杀订单

&#x20;                                                             ▼

&#x20;                                                    order 表(seckill\_activity\_id 非空)

&#x20;                                                             │

&#x20;                                                             │ 超时/手动取消
```

## 5. 数据库设计

### 5.1 新增表：`seckill_activity`



```
\-- sql/seckill\_module.sql

USE \`agsell\`;

DROP TABLE IF EXISTS \`seckill\_activity\`;

CREATE TABLE \`seckill\_activity\` (

&#x20;   \`id\`             BIGINT        NOT NULL AUTO\_INCREMENT COMMENT '主键',

&#x20;   \`product\_id\`     BIGINT        NOT NULL COMMENT '商品ID',

&#x20;   \`product\_spec\_id\` BIGINT       DEFAULT NULL COMMENT '绑定规格ID（无规格为NULL，秒杀按商品维度）',

&#x20;   \`seckill\_price\`  DECIMAL(10,2) NOT NULL COMMENT '秒杀价',

&#x20;   \`seckill\_stock\`  INT           NOT NULL DEFAULT 0 COMMENT '秒杀库存（活动放出的名额）',

&#x20;   \`seckill\_limit\`  INT           NOT NULL DEFAULT 1 COMMENT '每人限购数量',

&#x20;   \`start\_time\`     DATETIME      NOT NULL COMMENT '开始时间',

&#x20;   \`end\_time\`       DATETIME      NOT NULL COMMENT '结束时间',

&#x20;   \`status\`         TINYINT       NOT NULL DEFAULT 1 COMMENT '状态 0=下架 1=上架',

&#x20;   \`sort\`           INT           NOT NULL DEFAULT 0 COMMENT '排序值，越大越靠前',

&#x20;   \`create\_time\`    DATETIME      NOT NULL DEFAULT CURRENT\_TIMESTAMP COMMENT '创建时间',

&#x20;   \`update\_time\`    DATETIME      DEFAULT NULL ON UPDATE CURRENT\_TIMESTAMP COMMENT '更新时间',

&#x20;   \`deleted\`        TINYINT       NOT NULL DEFAULT 0 COMMENT '软删除标记',

&#x20;   PRIMARY KEY (\`id\`),

&#x20;   KEY \`idx\_product\_id\` (\`product\_id\`),

&#x20;   KEY \`idx\_status\_time\` (\`status\`, \`start\_time\`, \`end\_time\`)

) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4\_unicode\_ci COMMENT='秒杀活动表';
```

管理端建活动校验规则（服务端强制）：



* `seckill_price > 0` 且 **< 商品现价**（秒杀必须有折扣语义）；

* `seckill_stock > 0` 且 **≤ 商品 / 规格可用库存**（保证支付扣减兜底不失败）；

* `end_time > start_time`；

* 同商品允许存在多个活动（不同时段），但**时间区间不允许重叠**（防止同一商品同时两个秒杀价）。

### 5.2 订单表扩展（`order`）



```
ALTER TABLE \`order\`

&#x20;   ADD COLUMN \`seckill\_activity\_id\` BIGINT DEFAULT NULL COMMENT '秒杀活动ID（非秒杀订单为NULL）' AFTER \`remark\`,

&#x20;   ADD UNIQUE KEY \`uk\_user\_seckill\` (\`user\_id\`, \`seckill\_activity\_id\`);
```



* 秒杀订单：`seckill_activity_id` 非空，`pay_amount = seckill_price`；

* 普通订单：`NULL`，唯一索引不生效，零影响；

* **不新增秒杀订单表**，秒杀订单就是普通订单（复用订单列表 / 详情 / 支付 / 售后全链路，管理端只需在详情 VO 里透出 "秒杀活动" 标识）。

## 6. 后端设计

### 6.1 Redis Key 设计



| Key                          | 类型           | 说明                                                                      | 过期策略                            |
| ---------------------------- | ------------ | ----------------------------------------------------------------------- | ------------------------------- |
| `seckill:activity:{id}`      | String(JSON) | 活动快照：productId/specId/seckillPrice/stock/limit/startTime/endTime/status | 建活动 / 更新时写入，删除时清除               |
| `seckill:stock:{id}`         | String(int)  | 剩余秒杀库存                                                                  | 随活动快照写入                         |
| `seckill:user:{id}:{userId}` | String       | 用户已抢标记 `1`                                                              | 订单超时 / 手动取消时 DEL；支付成功保留（一人一单终身） |

> 快照缓存写入时机：活动创建 / 编辑 / 上下架时由管理端服务同步写 Redis；Redis 无缓存时懒加载（查 DB 后回填），保证 DB 为唯一事实来源。

### 6.2 核心 Lua 脚本（防超卖 + 防重复原子完成）



```
\-- KEYS\[1] = seckill:stock:{id}

\-- KEYS\[2] = seckill:user:{id}:{userId}

\-- ARGV\[1] = userId

\-- 返回：1=成功  0=已售罄  -1=活动未初始化/不存在  -2=已参与过

local stock = tonumber(redis.call('GET', KEYS\[1]) or '-1')

if stock < 0 then return -1 end

if stock <= 0 then return 0 end

if redis.call('EXISTS', KEYS\[2]) == 1 then return -2 end

redis.call('DECR', KEYS\[1])

redis.call('SET', KEYS\[2], '1')

return 1
```

单次网络往返完成 "查库存 + 扣库存 + 查重 + 标记"，无竞态窗口，这是防超卖 / 防重复的根本保证。

### 6.3 秒杀下单时序（`SeckillService.createSeckillOrder`）



```
1\. 用户已登录（BaseContext），校验 addressId 归属（复用订单逻辑口径）

2\. 读活动快照（Redis → 无则 DB 加载回填）

&#x20;  ├─ status != 1            → SECKILL\_ENDED

&#x20;  ├─ now < startTime        → SECKILL\_NOT\_STARTED

&#x20;  ├─ now > endTime          → SECKILL\_ENDED

&#x20;  └─ 商品已下架/不存在        → NOT\_FOUND\_ERROR

3\. 执行 Lua 脚本原子扣减

&#x20;  ├─ 返回 0  → SECKILL\_SOLD\_OUT（手慢了）

&#x20;  ├─ 返回 -2 → SECKILL\_REPEAT（已参与过）

&#x20;  └─ 返回 -1 → 缓存异常，尝试 DB 直查兜底，仍失败 → SYSTEM\_ERROR

4\. 构建秒杀订单（服务端计价，不信任前端）：

&#x20;  order.order\_no = AGS + 雪花ID（复用生成器）

&#x20;  order.pay\_amount = seckill\_price（非原价）

&#x20;  order.status = 0 待付款（复用 OrderStatusEnum）

&#x20;  order.seckill\_activity\_id = 活动ID

&#x20;  order\_item: price = seckill\_price、quantity = 1、快照商品名/图

5\. 插入 order + order\_item（事务）

6\. 失败补偿：若第 5 步异常（如唯一索引冲突 → SECKILL\_REPEAT），

&#x20;  回补 Redis：INCR 库存 + DEL 用户标记（保证名额不丢）

7\. 返回 OrderCreateVO（复用，前端走既有支付流程）
```

限购数量 `seckill_limit`：本期固定每单 1 件（`quantity=1`），`seckill_limit` 字段预留多购扩展（下单时校验 `已购 + 1 ≤ limit`）。

### 6.4 名额释放（闭环）

触发点两处，均幂等：



| 触发       | 位置                                        | 动作                                                                                           |
| -------- | ----------------------------------------- | -------------------------------------------------------------------------------------------- |
| 订单超时自动取消 | `OrderServiceImpl.cancelExpiredOrders` 改造 | 取消后若 `seckill_activity_id` 非空 → `INCR seckill:stock:{id}` + `DEL seckill:user:{id}:{userId}` |
| 用户手动取消   | `OrderServiceImpl.cancelOrder`            | 同上                                                                                           |

释放幂等设计：`DEL` 前先 `EXISTS` 判断（Redis 内用简单 Lua 或 "先 EXISTS 再 DEL"），避免重复取消时重复 `INCR` 造成库存虚高；以 "用户标记存在" 作为唯一释放凭据。

改造说明：`cancelExpiredOrders` 由 "纯批量 UPDATE" 改为 "查询超时待付款订单（limit 500）→ 逐单原子 UPDATE（保留状态守卫）→ 秒杀单释放"，每分钟处理上限 500 单，演示量级足够且保留原子性。

## 9. 测试计划

### 9.1 单元测试（`SeckillServiceImplTest`）



| 用例                  | 断言                                               |
| ------------------- | ------------------------------------------------ |
| 活动未开始 / 已结束 / 已下架下单 | 抛对应错误码                                           |
| 库存为 0 下单            | SECKILL\_SOLD\_OUT                               |
| 同用户重复下单             | SECKILL\_REPEAT（Redis 标记 + DB 唯一索引双路径）           |
| 下单成功                | 订单金额 = 秒杀价、seckill\_activity\_id 正确、Redis 库存 - 1 |

### 9.2 并发测试（核心演示）

`CountDownLatch + ExecutorService`：100 线程并发抢 50 库存活动：



* 断言成功下单 **恰好 50 笔**（不超卖）；

* 每单金额 = 秒杀价。

### 9.5 实现偏差记录（与文档定稿的差异）

1. **ObjectMapper 注入**：Spring Boot 4.1（webmvc starter）未自动注册 Jackson ObjectMapper Bean，`SeckillRedisServiceImpl` 改为自建静态实例（`new ObjectMapper().registerModule(new JavaTimeModule())`），不依赖容器自动配置。
2. **日期格式契约**：Jackson 3（tools.jackson）默认仅解析 ISO 格式（`2026-09-12T15:58:35`），管理端 `el-date-picker` 的 `value-format` 设为 `YYYY-MM-DDTHH:mm:ss`，与后端解析对齐。
3. **并发测试清理**：按商品无条件删除测试活动（而非时间窗口），保证压测幂等可重复。
4. **活动编号（防枚举爬取）**：自增主键不对小程序端暴露。`seckill_activity` 新增 `activity_code`（16 位随机大写字母数字 + 唯一索引兜底），用户端详情/下单改用编号：`GET /api/seckill/detail/{code}`、下单请求体 `activityCode`；管理端列表"ID"列改为"活动编号"。存量数据执行 `sql/seckill_module.sql` 中注释的 ALTER + 回填语句。
5. **日期选择器体验**：管理端活动时间由 `datetimerange` 双日历面板改为两个 `type="datetime"` 选择器（选完时间自动收起面板），并增加起止联动校验（结束时间 ≤ 开始时间时清空并提示）。

## 11. 风险与边界



| 风险             | 应对                                                           |
| -------------- | ------------------------------------------------------------ |
| Redis 宕机导致无法抢购 | 活动查询走 DB 兜底；下单遇 Redis 异常返回系统错误并告警日志，**不静默超卖**（DB 唯一索引仍防重复）   |
| 商品实际库存 < 秒杀库存  | 管理端建档强校验 `seckill_stock ≤ product.stock`；支付扣减失败订单保持待付款，可人工处理 |
| 多实例部署一致性       | Redis 操作天然原子，无本地锁；DB 唯一索引全局生效                                |
| 缓存与 DB 不一致     | 唯一事实来源为 DB，快照仅用于读优化；每次写操作同步刷新                                |
| 时间校验精度         | 应用层校验到秒级；极端边界（整点并发）由 Lua 库存判负兜底，不允许超卖                        |

## 12. 答辩问题预演（Q\&A）

**Q：秒杀如何防止超卖？**

A：三层。① Redis Lua 原子脚本 "查库存→扣库存→标记用户" 单次往返完成，无竞态窗口；② 支付时 DB 乐观锁（`stock >= quantity` 条件 UPDATE）兜底；③ 活动库存 ≤ 商品实际库存的建档校验兜底。

**Q：如何防止一个人抢多单？**

A：Redis `SETNX` 用户标记毫秒级预检 + `order` 表 `(user_id, seckill_activity_id)` 唯一索引持久兜底，且该索引对普通订单（NULL）不生效，零侵入。

**Q：抢到了不付钱怎么办？**

A：订单超时自动取消（复用现有 30min 超时任务），取消时原子回补 Redis 库存并清除用户标记，名额释放给下一位。

**Q：为什么不用消息队列？**

A：演示量级下单事务 10\~20ms，同步处理即可稳定支撑；引入 MQ 会增加可靠投递 / 死信等复杂度。生产环境可将下单异步化削峰，属扩展点。

**Q：Redis 挂了怎么办？**

A：活动读取降级 DB；下单遇 Redis 异常快速失败不超卖；防重复由 DB 唯一索引最终兜底。
