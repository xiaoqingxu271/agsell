## 1. 项目概述

### 1.1 项目背景

随着乡村振兴战略的深入推进和互联网经济的蓬勃发展，农产品上行（农产品从产地直供城市消费者）已成为重要的民生课题。传统农产品销售渠道存在**信息不对称、中间环节多、损耗率高、溯源困难**等痛点。本项目旨在设计并实现一套轻量级、易部署的农产品/特产销售系统，打通"产地—平台—消费者"的直连链路。

### 1.2 项目目标

- 构建一套完整的农产品电商交易系统（三端一体）
- 实现用户浏览、选购、下单、支付的完整购物闭环
- 实现管理员对商品、订单、用户、内容的全面运营管控
- 体现农产品特色（产地溯源、时令推荐、新鲜度标识）
- 满足本科/专科毕业设计的完整性和可答辩性要求

### 1.3 系统边界

**系统包含**：
- 后端 API 服务（Spring Boot 单体）
- 独立 AI 服务（Python：FastAPI + LangGraph + RAG 知识库 + 大模型智能体 + 智能导购）
- 管理后台 Web 应用（Vue 3 + Element Plus，含 AI 知识库维护页）
- 微信小程序用户端（uni-app 跨端框架，一套代码编译微信小程序 / H5）

**系统不包含**：
- 商家入驻系统（后台直接由管理员添加商品，暂不做多商家模式）
- 物流配送系统对接（模拟配送状态流转）
- 支付对接（模拟支付流程，支持微信支付接口预留）

### 1.4 核心业务流程

```
[用户端] 浏览商品 → 加入购物车 → 提交订单 → 模拟支付 → 查看订单状态
                          ↓
                    待发货 → 待收货 → 已完成 → 评价
                          ↓
                    退款/售后

[管理端] 商品管理 → 订单处理 → 发货 → 售后处理 → 数据分析
```

### 2.3 部署架构

```
开发环境：
  本地开发：IDEA（后端）+ VS Code（管理端）+ 微信开发者工具（小程序）
  
生产/演示环境：
  Linux 服务器（或 Docker）
  Nginx → 反向代理管理后台静态资源 + 转发 API 请求
  Spring Boot → 后端服务（8080）
  MySQL → 数据库（3306）
  Redis → 缓存（6379）
```

## 4. 功能需求 — 用户小程序端

### 4.1 首页

#### 4.1.1 功能描述
首页是用户进入小程序的第一个页面，承担流量分发和商品推荐的核心职责。

#### 4.1.2 功能列表

| 功能点 | 描述 | 优先级 |
|--------|------|:------:|
| 轮播 Banner | 顶部轮播图，展示促销活动、新品推荐 | P0 |
| 搜索栏 | 支持关键词搜索商品，点击跳转搜索结果页 | P0 |

## 6. 功能需求 — AI 智能客服与智能导购

> 本章对应题目《基于 RAG 与大模型智能体的农产品电商智能导购系统的设计与实现》的三个关键词：
> **RAG**（6.2、6.3）、**大模型智能体**（6.3、6.4）、**智能导购**（6.5、6.6、6.7）。
> 实现落在独立的 Python 服务 `ai-service`（FastAPI + LangGraph + Chroma + 本地 bge 向量模型 +
> Agnes 大模型），Java 主系统负责鉴权、业务数据与转发；两边只做 HTTP 通信，密钥不下浏览器。

### 6.1 功能描述

系统提供三类 AI 能力，共用一条对话链路：

1. **知识问答（RAG）**：运费、退换货、支付、秒杀、溯源等平台规则与常识问题，只能依据知识库条目回答；
2. **业务查询（工具）**：订单、物流、售后进度等用户私有数据，必须经服务端回调 Java 取数，不接受用户口述；
3. **智能导购**：为用户挑商品并给理由，结果以可点击的商品卡呈现，能回答"这件商品适不适合/能放多久"。

三条能力的共同约束是**反幻觉**：没有依据就不编造，宁可拒答并引导人工，也不能给出看似合理的假答案。

#### 6.1.1 功能列表

| 功能点 | 描述 | 优先级 |
|--------|------|:------:|
| 流式对话 | SSE 逐字下发回复，业务取数阶段不向用户暴露内部术语 | P0 |
| 知识库问答 | 双路召回（向量 + 关键词）后由大模型组织答案 | P0 |
| 拒答闸门 | 检索零命中/低于阈值时输出确定性拒答话术，不经大模型 | P0 |
| 工具编排智能体 | 由大模型决定调用哪些工具（可一轮并行多个），有界循环 | P0 |
| 业务数据查询 | 订单/物流/售后三类私有数据查询，强制校验归属 | P0 |
| 智能导购 | 语义召回 + 品类词 + 商详上下文 + 热销兜底五级通道 | P0 |
| 商品卡片 | 推荐结果以图片/价格/产地卡片呈现，可点进详情、可加购 | P0 |
| 商详页上下文 | 从商品详情页进客服时携带该商品事实，"这个"有明确指代 | P1 |
| 个性化重排 | 首页 feed / 搜索框 / 对话导购共用一套排序口径 | P1 |
| 转人工 | 强诉求或超能力范围时给出人工通道，并落一张工单到管理后台跟进（6.10） | P1 |
| 引用展示 | 知识问答的回复下方展示"依据"标签（服务端按检索命中结构化下发，不经模型复述） | P1 |

### 6.2 RAG 知识库问答

#### 6.2.1 功能描述

知识库以 MySQL `ai_faq` 为数据源，Chroma 向量库为召回索引，嵌入模型本地推理（bge-small-zh-v1.5，
cosine 距离）。检索采用三路：向量语义召回 + MySQL ngram 全文召回（BM25 相关度）+ `ai_faq.keywords`
关键词精确命中（每条命中 +0.5 分）；三路按归一分数线性加权融合（向量余弦分原样、
全文相关度按本查询命中集归一后乘 0.3）。曾实测 RRF(k=60) 方案：它把"两路排名相同"的
条目分数压到几乎相等，向量距离信息丢失，人工改写集上生产路径 Hit@1 从 90.3% 退化到
83.3%，故弃用——选型对比有存档。
全文通道与关键词通道是词面证据通道，但必须过词面校验（查询按停用词切段后，任一 ≥2 字段
命中条目问句+答案原文）——"推荐一部电影"剥掉"推荐"后无法命中原文，域外拒答语义不回退。
任一通道故障自动退场（向量+关键词两路照常），检索层永不因单通道故障对用户报错。
命中的条目同时以 `references`（id+问句）结构化下发，前端渲染"依据"标签。

#### 6.2.2 功能列表

| 功能点 | 描述 | 优先级 |
|--------|------|:------:|
| 三路召回 | 向量 top-k + 全文 BM25（词面校验）+ `ai_faq.keywords` 关键词加权，线性加权融合后回填答案 | P0 |
| 阈值拒答 | 全部命中低于 `KB_SCORE_THRESHOLD` 时不送大模型，直接返回确定性话术 | P0 |
| 增量索引 | FAQ 新增/修改自动 upsert，停用与删除自动从索引下架 | P0 |
| 全量重建 | 管理页一键按启用条目重算索引（兜底修复） | P1 |
| 长文档切分 | 大段知识按语义分块入库（当前条目粒度短，列为后续） | P2 |

#### 6.2.3 验收口径

- 知识库 280 条全覆盖评测：人工改写问法的命中率、扩容后各分类覆盖完整（见量化实验报告 §4）。
- 域外问题（股票、天气、影视等）拒答率实测 91.7%，且拒答路径零大模型调用、输出确定（§6）。

### 6.3 大模型智能体工具编排

#### 6.3.1 功能描述

把 6 项能力注册为 function schema，由大模型自主规划调用；规则层只保留高置信、零成本、
不需要取数的判断（转人工强诉求词、纯寒暄）做毫秒级短路。旧实现是"意图分类 argmax → 固定单分支 →
调一个工具"，一句话带两个诉求只能答一半，实测规则通道在未参与调参的 hold-out 集上只有 37.6%
（无词面线索子集 23.4%），本来就承担不了语义分类。

#### 6.3.2 功能列表

| 功能点 | 描述 | 优先级 |
|--------|------|:------:|
| 工具目录 | `kb_search` / `product_search` / `order_query` / `logistics_query` / `after_sales_query` / `escalate_human` | P0 |
| 并行取证 | 同一规划步可发起多个工具调用，一次回复覆盖多个诉求 | P0 |
| 有界循环 | 最多 `AGENT_MAX_STEPS` 步、单轮最多 `AGENT_MAX_TOOL_CALLS` 次调用 | P0 |
| 调用去重 | 按 (工具, 参数) 去重，重复调用只回灌提示不再执行 | P0 |
| 反思改写 | 工具返回空结果时允许换检索表述重试一次 | P1 |
| 提前退出 | 本步资料可用即结束编排，不多花一次上游往返（实测单次规划 6~15 s） | P1 |
| 能力协商降级 | 上游不支持 function calling 或规划异常时退回"分类 + 单工具"并告警 | P0 |
| 中间过程不外显 | 规划的 tool_calls 与空回复一律不进 token 流 | P0 |

#### 6.3.3 验收口径

- 工具选择准确率 86.2%（hold-out 全集 109 条，两次独立测量同分）；同一批题规则通道 37.6%（§8）。
- 一句多诉求实测 2 次大模型调用即可完成，代价与单诉求同级（§5.4）。

### 6.4 业务数据查询与隐私保护

| 功能点 | 描述 | 优先级 |
|--------|------|:------:|
| 归属校验 | Java 内部接口按 JWT 解出的 userId 过滤，他人订单返回 40400 | P0 |
| 隐私最小化 | 返回给 AI 的订单 VO 不含收货人、电话、地址 | P0 |
| 未登录引导 | 无 userId 时不回调 Java，直接给登录引导话术 | P0 |
| 跨轮隔离 | 会话状态按"服务端可信 userId + sessionId"分线程存放，他人无法借 sessionId 接管 | P0 |
| 本轮临时数据重置 | 每轮开始清空上一轮的工具结果，避免答非所问与复述上一轮隐私 | P0 |
| 错误脱敏 | 上游异常只发 code，前端按白名单文案展示；内部地址/模型名不进用户端 | P0 |

### 6.5 智能导购

#### 6.5.1 通道与闸门

| 顺序 | 通道 | 采信依据 |
|:----:|------|----------|
| ⓪ | 商详页指代 | 有 productId 且模型未点出品类词 ⇒ 问的就是眼前这件（指代句与真品类问句的向量分重叠，阈值不可分） |
| ① | 品类词 LIKE | 商品名里真有这个词，是最硬证据，排在卡片列表最前 |
| ② | 语义召回 | 对话侧独立闸门 `REC_MIN_SCORE=0.47`（搜索框用 0.35，场景不同不可混用），并补齐 LIKE 的单薄结果 |
| ③ | 域外拒答 | 两路皆空 + 模型判定不属经营范围 ⇒ 确定性拒答，不降级热销榜 |
| ④ | 热销兜底 | 未拿到经营域判定时不拒答（故障期行为与改造前一致） |

登录用户叠加个性化重排（类目偏好 + 销量 + 好评率 + 新鲜度），但 LIKE 命中组重排后仍置顶。
类目偏好由六路信号合并（各路归一后按权重加权）：订单 0.5（已验证的真实选择）、收藏 0.35（显式强意向）、
好评 0.3、加购 0.3（临门一脚）、浏览 0.2（带 3 天半衰期时间衰减）、搜索词 0.15（关键词 LIKE 在售
商品名映射到品类，近 7 天窗口）；游客不叠加偏好项。

#### 6.5.2 商品卡片与口碑表述

| 功能点 | 描述 | 优先级 |
|--------|------|:------:|
| 结构化下发 | 候选以 `items` 事件独立下发，卡片先于回复文本到位 | P0 |
| 可点击 | 卡片点进商品详情，支持快捷加购 | P0 |
| 顺序一致 | 介绍顺序必须与候选顺序一致（否则卡片顺序和说的话对不上） | P1 |
| 口碑成句 | `reviewCount/positiveRate/topKeywords` 由服务端拼成一句成品话术，卡片与大模型上下文同源 | P0 |
| 零评价不谎称 | 无评价数据显示"暂无评价数据"，不得出现"好评率高/口碑不错" | P0 |
| 指标不混用 | 关键词不得说成"回购率"，销量不得说成"回购人数" | P0 |

### 6.6 多轮会话与商详上下文

| 功能点 | 描述 | 优先级 |
|--------|------|:------:|
| 会话记忆 | LangGraph checkpointer 按 thread 维持多轮（本地 SQLite 持久化，可选 Redis） | P0 |
| 历史窗口截断 | 按字符预算保留最近对话，系统提示词常驻、从完整人类轮次起 | P1 |
| 指代补全 | 规划器读取最近若干轮历史补全检索句；工具参数缺省时执行器按规则改写召回串（短追问/指代词自动携带上一条用户消息，零 LLM 成本） | P1 |
| 商品上下文 | 从商详页进客服携带 productId，回答"这个能放多久/适合送礼吗" | P1 |
| 上下文条 | 聊天页顶部显示正在咨询的商品，可一键清除 | P2 |

### 6.7 首页推荐与搜索联动

同一份混合排序与同一套向量索引服务三处入口（首页 feed、搜索框语义召回、对话导购），
避免"同一件商品换个入口分数就变"。商品新增与上下架后由 Java 异步通知增量更新索引，
管理页保留全量重建兜底。

### 6.8 性能与额度约束（非功能）

| 指标 | 目标 / 实测 | 说明 |
|------|-------------|------|
| 寒暄首 token | ≈ 2~3 s | 规则前置直出，只花一次大模型调用 |
| FAQ 问答首 token | ≈ 9.6 s | 规划 + 作答两次串行调用 |
| 导购首 token | 19.2 s → 11.1 s → 10.5 s | 三次调用 → 两次 → 智能体（同一改动链路的三轮复测） |
| 取证阶段完成 | P50 ≈ 2.2 s | 工具跑完即下发卡片 |
| 拒答路径成本 | 0 次大模型调用 | 闸门命中时直接输出确定话术，省额度且零幻觉 |
| 限流与退避 | 免费额度按窗口限流，客户端内置退避重试；额度故障不得计入能力评测 | 评测脚本会识别 429 并拒绝出数 |
| 服务可用性 | Java/向量库/大模型任一不可用时，用户只看到友好话术 | 不出现"系统错误"等内部文案 |

### 6.10 转人工工单闭环

#### 6.10.1 功能描述

「转人工」此前只回复一句客服电话话术，用户诉求与管理端动作之间没有记录。现在两条触发路径
（规则前置的强诉求短路、智能体的 `escalate_human` 工具）都会在 Python 侧回调 Java 内部接口
落一张 `ai_ticket`（用户原话 + 转人工原因 + 会话号，游客同样留痕），管理后台「AI 转人工工单」页
查看并处理，处理结果计入导航栏待办徽标。

#### 6.10.2 功能列表

| 功能点 | 描述 | 优先级 |
|--------|------|:------:|
| 工单落库 | 转人工触发后回调 `POST /api/ai/internal/ticket`，尽力而为（失败只记日志，不影响对话回复） | P1 |
| 原因采集 | 优先取模型给出的 `escalate_human` 入参原因，规则短路路径用中性文案兜底 | P1 |
| 管理端列表 | 待处理排前、状态筛选、游客标识、会话号可回查上下文 | P1 |
| 处理工单 | 待处理 → 已处理原子抢占（防双管理员并发重复处理），处理备注可留 | P1 |
| 待办徽标 | 导航栏待办汇总增加「待处理工单」计数（`/admin/notice/summary`） | P2 |
| 权限 | 与知识库同口径：仅 SUPER_ADMIN 与 ADMIN（路径在 `/api/admin/ai` 禁入清单内） | P0 |

## 9. 非功能性需求

### 9.1 性能需求
- 首页加载时间 ≤ 2 秒（4G 网络环境下）
- API 接口平均响应时间 ≤ 500ms
- 支持同时 100+ 用户在线访问
- 商品图片压缩存储，单张 ≤ 200KB

### 9.2 安全需求
- 用户密码 BCrypt 加密存储
- JWT Token 有效期 24 小时（`JWT_EXPIRATION` 可配置），过期需重新登录；用户端与管理端 token 分类型隔离，Redis 存储会话支持服务端失效
- 管理后台接口统一鉴权（自研 JWT 拦截器 + 角色矩阵，未引入 Spring Security）
- AI 内部回调接口与服务间调用使用独立 `X-Internal-Key` 鉴权（未配置即拒绝，fail-closed）
- SQL 注入防护（MyBatis 参数化查询）
- XSS 防护（输入内容转义）
- 接口限流（AI 相关端点：对话/推荐 feed/浏览上报按调用主体每窗口限量，Redis 计数，Redis 故障时放行不扩大故障）

### 9.3 可用性需求
- 系统可用性 ≥ 99%（演示环境）
- 关键操作有明确的错误提示
- 表单提交前后端双重校验
- 文件上传限制类型和大小（图片 ≤ 5MB，仅 jpg/png/webp）

### 9.4 兼容性需求
- 管理后台兼容 Chrome、Edge、Firefox 最新版
- 小程序兼容微信基础库 2.25.0+
- 响应式布局适配 1280px 以上分辨率

### 9.5 可维护性需求
- 代码注释率 ≥ 15%
- 接口文档完整（Swagger / Apifox）
- 前后端分离，独立部署
- 数据库变更使用 `sql/migration/` 增量脚本管理（`docker/initdb.sh` 按依赖顺序执行，脚本幂等可重复执行）

## 10. 接口设计规范

### 10.1 统一响应格式

```json
{
  "code": 0,
  "message": "ok",
  "data": {}
}
```

**业务状态码定义**（与 `ErrorCode` 枚举一致，前端按 code===0 判成功）：

| code | 含义 |
|------|------|
| 0 | 成功 |
| 40000 | 请求参数错误 |
| 40100 | 未登录（用户端） |
| 40101 | 无权限 |
| 40200 / 40201 | 管理员未登录 / 管理员无权限 |
| 40400 | 请求数据不存在（含越权访问他人资源时的脱敏响应） |
| 50000 / 50001 | 系统内部异常 / 操作失败 |
| 50002 / 50003 | 库存不足 / 订单状态异常 |

### 10.2 分页响应格式

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "list": [],
    "total": 100,
    "page": 1,
    "pageSize": 15,
    "pages": 7
  }
}
```

### 10.3 认证方式
- 用户端：Header 中携带 `Authorization: Bearer {token}`
- 管理端：Header 中携带 `Authorization: Bearer {token}`
- Token 在登录成功后返回，前端存入 localStorage（管理端）/ wx.setStorageSync（小程序）

### 10.4 文件上传
- 接口：`POST /api/upload`
- 返回格式：`{ "url": "https://..." }`
- 支持 jpg/png/webp/gif，单文件 ≤ 5MB

```

    │                       │                        │
```

### 13.2 农产品特色功能说明

本系统针对农产品/特产销售场景设计了以下特色功能：

1. **产地溯源信息**：每个商品可记录产地、采摘日期、运输方式，增强消费者信任
2. **新鲜度标识**：根据采摘日期自动计算并展示"新鲜度"标签
3. **时令推荐**：首页根据当季商品自动推荐时令产品
4. **保鲜说明**：商品详情展示储存方式、保质期、冷链配送说明
5. **坏果包赔**：售后流程支持"品质问题"退款，体现农产品特殊性
6. **可解释的智能导购**：对话推荐结果以商品卡呈现，理由只用商品真实字段（价格/产地/销量/储存/保质期/口碑），
   零评价商品显示"暂无评价数据"而非好评率；口碑句子由服务端拼好后原样引用
7. **知识来源可维护且即时生效**：管理端改一条 FAQ 即同步向量索引，客服当场按新答案回答，
   索引条数与启用条数不一致时页面直接告警

#### 农产品溯源体系（特色模块）

针对农产品"信任缺失"的核心痛点，系统设计了一套完整的溯源体系：

- **批次管理**：每批商品绑定唯一批次号，关联种植/采摘/质检全流程记录
- **二维码溯源**：每个批次生成独立二维码，消费者扫码即可查看完整溯源信息
- **种植档案**：记录播种、施肥、浇水、采收等生产过程及时间线
- **质检报告**：支持上传农药残留检测报告、有机认证等资质文件
- **生产者信息**：展示种植户姓名、联系电话、产地地址，建立"从农田到餐桌"的信任链

#### 时令产品管理（本期实现范围）

- **新鲜度计算**：按采摘/上市日期与保质期计算 0~1 新鲜度分，参与导购与推荐排序（已实现，`ai-service/app/rag/freshness.py`）
- **应季推荐**：推荐理由可出现"时令"类标签（新鲜度信号择优），首页 feed / 搜索框 / 对话导购共用同一排序口径（已实现）
- 上市开始/结束日期区间与预售模式未在本期实现，列入 13.4 扩展方向

### 13.3 技术难点及解决方案

| 难点 | 解决方案 |
|------|----------|
| 并发库存扣减 | 使用 Redis 预减库存 + 数据库乐观锁（version 字段） |
| 订单超时自动取消 | 使用 Spring Schedule 定时任务扫描超时未支付订单，自动取消并回滚库存 |
| 图片上传与存储 | 本地 MinIO 存储 + Nginx 静态资源服务；或对接阿里云 OSS |
| JWT 无状态认证 | Spring Security Filter 拦截 + Token 续签机制（临近过期自动刷新） |
| 多规格商品选择 | 规格表独立设计，购物车和订单中保留规格快照，防止商品信息变更影响历史订单 |
| 富文本图片上传 | 富文本编辑器集成图片上传接口，返回 URL 插入 |
| 溯源二维码生成 | 使用 ZXing 库生成二维码，每个批次绑定独立 URL（如 `https://xxx.com/trace?batch=xxx`） |
| 秒杀并发控制 | Redis 预扣库存 + 数据库乐观锁 + 防重提交（用户粒度去重） |
