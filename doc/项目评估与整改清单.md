# 项目全面评估与整改清单

> 对照题目《基于 RAG 与大模型智能体的农产品电商智能导购系统的设计与实现》逐项核查。
> 评估日期：2026-10-17。所有结论均标注证据位置（文件:行号）；标「需实测」的是代码推断、尚未跑数据验证的项。
> 状态口径：**已验证** = 读代码/读存档数据确认；**需实测** = 需跑一次脚本或点一次页面确认。

---

## 0. 总体判断

工程完成度高于一般毕设：三端 + 独立 AI 服务、21 张业务表 + 1 张知识库表、32 个控制器、35 个测试类、
SSE 流式全链路、限流/降级/越权防护/隐私最小化都做了，量化实验也有真实存档。
问题不在"做得少"，而在**三个题目关键词的强度不匹配**：

| 题目关键词 | 现状 | 判定 |
|---|---|---|
| RAG | 有向量检索 + 阈值拒答 + 双路召回，但知识库是 280 条人工 QA 对，没有切分/重排/查询改写/引用展示 | **及格偏上，但不像"RAG 系统"** |
| 大模型智能体 | LangGraph 固定拓扑：意图 argmax → 单分支 → 单工具一次 → 生成。**没有 tool-calling、没有循环、没有反思/重规划** | **最薄弱，答辩必被追问** |
| 智能导购 | 语义召回 + 个性化混合重排 + 可解释理由（这块做得最好）。但聊天页只回纯文本，推荐商品**没有卡片、点不进商详、加不了购** | **算法强、闭环断** |

结论：优先补「智能体证据」和「导购闭环 UI」，其次修实验数据一致性与复现环境，再考虑功能加项。

## 1. P0：会当场被问穿 / 阻塞复现

### 1.1 「大模型智能体」的实现其实是工作流，不是智能体（已验证）

- 拓扑固定、单向无环：`ai-service/app/agent/graph.py:43-67` —— `START → intent →（条件路由，单支）→ 一个工具节点 → generate → END`。
- 每轮**只调用一个工具、且只调用一次**：`nodes.py:64-78` 的 `route_by_intent` 是 argmax 单标签，没有并行工具、没有多跳。
- 没有 function/tool calling：全仓无 `bind_tools` / `tool_call`；LLM 只做「分类」和「写作」两件事，检索/查询的选择权在人工写死的 if-else 里。
- 没有反思与重试：工具返回空只把空结果原样交给生成节点（`nodes.py:227-229`），不改写查询再试一次。
- 多意图表达只走一支："我上周买的那个芒果物流到哪了，顺便再帮我推荐类似的" → 只能命中 `logistics` 或 `recommend` 之一。

**答辩风险**：老师问"你的智能体体现在哪里？跟普通 if-else 分发有什么区别？"目前没有正面答案。

**建议改法（约 1~2 天，收益最大）**：把 FAQ 检索、商品检索、订单、物流、售后、优惠券这 6 个能力注册成
OpenAI function schema，用 `llm.bind_tools(...)` 跑一个**有界的 ReAct 循环**（最多 3 步），保留现有意图识别作为
"高置信短路"通道（低成本路径），并加一条反思边：工具空结果 → LLM 改写查询重试 1 次。论文里就能写出
「Plan-Act-Reflect + 工具编排」的智能体章节，且现有 4 个降级路径全部可复用。

### 1.2 导购结果在小程序里是一段纯文本，闭环断在最关键的落点（已验证）

- `agsell-uniapp/src/pages/ai-chat/chat.vue:14-56`：只有气泡文字 + 下一轮建议 chips，**没有商品卡片、图片、价格，不可点击**。
- 数据其实是有的：`AiInternalController.productSearch` 返回 `mainImage/price/sales/positiveRate`
  （`src/main/java/.../AiInternalController.java:220-239`），`format_payload` 把它们塞成文本进 `tool_result`，
  图片与跳转信息到 LLM 手里就丢了。
- `RECOMMEND_SYSTEM_PROMPT` 第 5 条还写着"引导用户去小程序搜索或加购"（`ai-service/app/prompts.py:47`）——
  等于承认了要用户自己再去搜一遍。

**建议**：SSE `done` 事件额外下发结构化 `items`（id/name/price/mainImage/reason），聊天页渲染商品卡，点击进详情页、
长按直接加购。这是"智能导购系统"最该展示的一屏，改动小、演示冲击力最大。

### 1.3 多轮导购丢约束，与"多轮会话记忆"的宣称冲突（已验证）

- `nodes.py:186-188`：语义召回和偏好抽取都只取 `state["messages"][-1]`，历史只进生成节点的 prompt。
- 后果：「有什么水果推荐」→「有没有便宜点的」时，第二次召回的 query 就是"有没有便宜点的"这六个字，
  上一轮的"水果"和价格意图都不继承；`RECOMMEND_EXTRACT_PROMPT` 也只抽 `keyword/maxPrice` 两个字段
  （`prompts.py:31-38`），无最低价、无规格、无人数、无用途。
- 建议：召回 query = 最近 2~3 轮拼接，或让 LLM 基于历史做一次 query rewriting —— 顺带把 RAG 缺的「查询改写」补上，一举两得。

### 1.5 量化实验报告与实验存档不一致，且缺了"导购"这场主实验（已验证）

### 1.6 意图实验存在测试集污染，且新数据显示规则通道打赢了 LLM（已验证）

- `eval_intent.py:97-102`：`--mode keyword` 跑的是 `_hard_rule(q) or _keyword_fallback(q)`，即生产规则全量；
  `--mode llm` 跑 `classify_intent`（规则前置 + LLM + 兜底）。
- `intent.py:56-60` 的注释自己写了"**在 103 题测试集上对其他意图零误伤**"—— 规则就是照着这份测试集调出来的。
- 于是最新存档里出现：**规则 96.12% > 生产（含 LLM）86.41%**。两次测量还不同日（LLM 10-05、keyword 10-10），
  不能直接比。

**这条必须主动处理**，否则老师一句"规则更准更省，为什么要用大模型"就答不住。建议：
新标一份 100~150 条 **hold-out** 测试集（不参与规则调试），同日重跑 规则 / LLM / 混合 三通道；
把结论改写成"规则覆盖高频表达、LLM 负责无关键词特征的语义类问法（如'第一次买不知道买啥'）"，
用**分意图分项**证明 LLM 的不可替代性，而不是比总分。

## 2. P1：题目要求但功能缺失

### 2.1 「收藏」整个模块不存在（已验证）

全仓 `favorite/收藏` 零命中：无表、无接口、无页面、商详页无收藏按钮。
两重损失：功能清单一处缺项；个性化少了一路**最强的正反馈信号**（比浏览可信、比下单稠密）。
现有偏好只有订单+好评+浏览三路（`ai-service/app/repositories/preference_repo.py`），
购物车加购、搜索词、收藏都还没用 —— 补收藏 + 把加购与搜索词并入偏好，是性价比最高的算法增量。

### 2.2 管理后台没有知识库维护页，Java 也没有代理（已验证）

- `ai-service/app/api/admin_kb.py` 有完整 CRUD + 增量索引同步（`:119-197`），但
  `agsell-frontend/src/views/admin/` 下 15 个页面里**没有任何 KB/FAQ 页**；Java 侧对 `faq/kb` 零引用。
- `doc/AI智能客服模块-技术栈设计.md:16` 的架构图明写了"Vue3 管理端（新增知识库/FAQ 维护页，阶段四 P2 可选）"，
  `seed_kb_extended.py:11` 的注释还写着"管理端 FAQ CRUD UI 现成" —— **注释与事实不符**。
- RAG 系统的知识库只能靠命令行维护，答辩演示时无法展示"运营改一条知识 → 索引即时生效"这条最有说服力的链路。

**建议**：加一页「知识库管理」（列表 + 分类筛选 + 编辑 + 索引状态），Java 侧做鉴权代理转 Python。约 1 天。

### 2.3 商品向量索引不自动重建，新上架商品 AI 召不到（已验证）

- `admin_kb.py:12`：「商品上下架低频，暂只在商品数据变更后**手动**调用 products/index 重建」。
- Java 商品发布/编辑/下架处无任何通知（`src/main/java` 全仓无 `products/index` 调用）。
- 后果：管理员上新 → 首页推荐、搜索框语义召回、AI 导购三处都召不到这个商品，且现场很难解释清楚。
- 建议：商品增改/上下架成功后异步 upsert 单条到索引（复用 `VectorStore.upsert_many`），KB 管理页再放一个"全量重建"按钮兜底。

### 2.4 转人工只有一句电话话术，没有人工闭环（已验证）

`prompts.py:59` 的 `HUMAN_FALLBACK_REPLY` 是纯文本，不建单、不通知、后台无处理页；
`AdminNoticeController` 只有 `/admin/notice/summary` 待办汇总。
"转人工"是智能客服系统的标准需求项，目前等于没有兜底闭环。建议做轻量「人工工单/留言」：
转人工时落一张 `ai_ticket`（会话上下文 + 用户 + 意图），后台列表可处理并回复。

### 2.5 首页铃铛是死按钮（已验证）

`agsell-uniapp/src/pages/index/index.vue:311-313`：`onNotifyTap()` 只弹 `toast('暂无新消息')`，无消息中心页。
点一下就被看穿；要么补订单/售后状态消息页（数据都现成），要么先把入口撤掉。

### 2.6 商详页进 AI 不带商品上下文（已验证）

- `agsell-uniapp/src/pages/product/product.vue:368`：`uni.navigateTo({url:'/pages/ai-chat/chat'})`，无 `productId`；
  `chat.vue:117 onLoad` 不解析任何参数。
- 用户从商品详情页点进客服，问"这个适合送礼吗/这个新鲜吗"时，系统不知道"这个"是哪个商品。
  知识库其实已有 `product_knowledge` 条目（`seed_kb_extended.py`），只是缺上下文注入。
- 建议：入口带 `productId`，进页面时注入一条隐式上下文（商品名/价格/产地），并给快捷问题「这个商品怎么样」。

### 2.7 推荐/导购链路的首 token 延迟没有实测（已验证）

`eval_latency.py:23-34` 只覆盖 smalltalk 与 faq 两组。导购分支是**三次串行 LLM 调用**
（意图分类 → 偏好抽取 → 生成），比实测的 7.3s 只会更慢。论文主角分支缺延迟数据，
而报告 §5 自己写了"两次串行即占 5s 以上"。补测 recommend 分支，并顺手实现"意图识别与召回并行"。

## 3. P2：RAG 深度可加分项（按性价比排序）

现状是"QA 对检索"，不是"文档库检索"。以下是把它做成真正的 RAG 系统的增量，任选 2~3 项即可显著提升论文厚度：

1. **长文档入库 + 切分策略**（`vectorstore.py:42-43` 目前是一条 FAQ = 一个向量，无 chunk 概念）：
   把商品详情长文本、`traceability_info`/`production_record` 生产记录、`review` 评价原文切块入索引。
   答辩问"你的切分与重叠策略"时才有答案，而且用户真会问"这批橙子什么时候采摘、怎么储存"。
2. **真正的混合检索**：`retriever.py:48-66` 的"关键词路"是 MySQL `FAQ.keywords` 子串命中，不是 BM25。
   商品表已有 ngram 全文索引（`sql/product_module.sql:57`），补 BM25/全文 + RRF 融合，命名才站得住。
3. **重排（rerank）**：召回 top-20 → `bge-reranker` 或 LLM listwise 重排 top-5。这是 Hit@1 提升最稳的一招。
4. **查询改写**：多查询 / HyDE / 基于对话历史的改写 —— 同时解决 1.3 的多轮丢约束。
5. **元数据过滤**：`category` 已写进 metadata（`vectorstore.py:46-51`）但检索从不传 `where`
   （`:106-108`）。"50 元以内的绿茶"这类约束应能在检索层过滤，而不是全靠 LLM 事后挑。
6. **引用展示**：答案下方列出"依据：《运费规则》"，可点开原文。反幻觉的可信度证据，前端一小块即可。
7. **情感分析基线对比**：`sentiment/analyzer.py` 是规则法（词库+否定翻转+程度副词+评分先验），确定性、零成本，
   很好；但论文若把它算作"AI 能力"，建议加一个朴素基线（FinBERT/中文情感分类模型或 LLM few-shot）做准确率对比表。

### 导购能力本身还可以往"智能体"方向长

- **商品对比**："这两个脐橙哪个好" → 并行取两件商品详情 + 口碑做结构化对比（天然需要多工具调用，正好撑 1.1）。
- **凑单/满减最优组合**：结合现有 `coupon`/`user_coupon` 模块，给定购物车推荐"再加一件 X 元即可用券"。
  业务约束计算 + LLM 解释，是"智能体有用"的强证据，而且和已实现的优惠券模块直接衔接。
- **时令/清单式导购**：一份"火锅食材清单""办公室零食清单"多商品组合推荐。
