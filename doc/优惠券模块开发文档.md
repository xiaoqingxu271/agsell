## 1. 模块概述

### 1.1 背景

需求文档 4.5.2「优惠信息展示（优惠券、满减等活动，预留）」列为 P2 功能，当前三端均未实现。与此同时，`order` 表自建表起就预留了 `discount`（优惠金额）与 `pay_amount`（实付金额）字段，但 `OrderServiceImpl.createOrder` 中 `discount` 一直写死为 `0.00`——**优惠落账点从未启用**。本模块补齐该能力，让「领券 → 结算选券 → 下单优惠 → 取消回退」形成完整闭环。

### 1.2 目标

| 端 | 能力 |
| --- | --- |
| 管理端 | 券模板建档 / 编辑 / 上下架 / 删除，控制面额、门槛、总量、每人限领、有效期 |
| 小程序端 | 领券中心、我的券包（未使用 / 已使用 / 已过期）、结算页选券与金额明细 |
| 后端 | 领取防超发 / 防重复领取、下单原子核销、取消与超时回退，复用现有订单 / 支付链路 |

### 1.3 答辩亮点（一句话总结）

**优惠券全生命周期闭环 + 双保险防超发**：Redis Lua 原子预扣拦截领取峰值 → DB 条件 UPDATE（`status=0` 守卫）兜底核销防双花；下单即锁定、取消/超时自动回退，全链路与秒杀模块同一套并发设计语言，可复用并发压测演示。

## 2. 现状与约束（探查结论）

以下为代码现状（2026-09-18 核实），优惠券设计必须对齐：

1. **优惠字段已预留、未启用**：`order` 表已有 `discount`（`NOT NULL DEFAULT 0.00`）与 `pay_amount`；`OrderServiceImpl.createOrder` 第 5 步 `order.setDiscount(BigDecimal.ZERO)`、`order.setPayAmount(totalAmount.add(freight))`——优惠券只需在计价处接入，**无需改金额字段，仅需追加券标识字段**。

2. **下单不扣库存，支付才扣**：`createOrder` 仅校验库存快照（快速失败），`PaymentServiceImpl.createPayment` 支付成功时乐观锁扣减（`stock >= quantity` 原子 UPDATE）。优惠券核销沿用同一精神：**下单创建时原子占用，支付不重复处理**（支付链路零侵入）。

3. **订单超时取消**：`OrderTimeoutScheduler` 每 60s 扫描，调 `OrderServiceImpl.cancelExpiredOrders` 批量置为已取消（单条原子 UPDATE + 状态守卫）。**优惠券回退钩子必须挂在这里**，与秒杀名额释放（`releaseSeckillQuota`）并列，防止丢券。

4. **Redis 已就绪且已有营销范式**：`SeckillRedisService` 已实现「Lua 原子脚本预扣库存 + 用户标记 + 释放补偿」，优惠券领取/核销直接复用同一套写法，无新依赖。

5. **秒杀模块是接入模板**：新表（`seckill_activity`）+ `order` 表加字段（`seckill_activity_id` + 唯一索引 `uk_user_seckill`，NULL 不参与冲突校验，普通订单零影响）+ 管理端 CRUD + 用户端列表/详情 + 取消/超时释放。优惠券完全复刻该路径。

6. **秒杀与优惠券天然互斥**：秒杀下单走独立入口 `SeckillService.createSeckillOrder`，不经 `createOrder`，秒杀订单不会携带 `couponId`；`createOrder` 内再做一次防御性拦截即可。

7. **管理端现状**：列表页统一在 `src/views/admin/list/*.vue`（如 `SeckillListView.vue`）；路由在 `src/router/guards.ts`；API 在 `src/api/admin.ts`；侧边栏在 `views/admin/LayoutView.vue`。

8. **小程序现状**：结算页 `src/pages/order/confirm/confirm.vue` **目前无任何优惠位**（已核实，discount/优惠/coupon 零匹配），金额明细只有商品金额 + 运费；API 封装在 `src/api/*.js`（如 `order.js`）；页面注册在 `src/pages.json`。订单详情 VO（`OrderDetailVO`）已返回 `discount`，展示优惠金额无需改后端 VO。

9. **错误码枚举**：`ErrorCode.java` 需新增优惠券专用错误码（见 6.6）。

## 3. 技术选型与量化对比

### 3.1 领取防超发：Redis 预扣 vs 纯 DB 条件更新

| 维度 | 纯 DB（直接 INSERT + 计数） | **Redis 原子预扣 + DB 兜底（本方案）** |
| --- | --- | --- |
| 并发峰值 | 单行 `received_count` 热点更新，串行等行锁，约 2~5k QPS | 内存 DECR 毫秒级，单实例 10 万级 |
| 超发风险 | 需 `UPDATE ... WHERE received_count < total_count` 条件更新，可防 | Lua 原子 DECR 判负，可防 |
| DB 压力 | 峰值全部打 MySQL | 99% 请求在 Redis 终结 |
| 复杂度 | 低 | 中（预热 + 释放补偿，与秒杀完全同构，可复制） |

**结论**：秒杀模块已把「Redis Lua + DB 唯一索引」双保险完整跑通并压测（100 并发 × 50 库存恰好 50 单、754ms），优惠券领取是同一并发模型（100 人抢 50 张券），直接复用该模式，边际成本几乎为零。

### 3.2 核销时机：下单即占用 vs 支付成功核销

| 维度 | 支付成功核销 | **下单即占用（本方案）** |
| --- | --- | --- |
| 并发双花风险 | 用户可开两个待付款订单同时用同一张券，支付时第二单核销失败，需回滚支付，复杂度高 | `createOrder` 内条件 UPDATE 原子核销，天然无双花 |
| 超时释放 | 需在支付/取消两处处理 | 与秒杀「下单占名额、取消释放」完全一致，钩子位置统一 |
| 用户感知 | 下单时未锁券，结算金额与实际优惠可能不一致 | 下单即见优惠金额，明确 |
| 实现成本 | 高（支付链路改动） | 低（仅改 `createOrder` + 取消两处） |

**结论**：采用**下单即占用**。与库存「支付才扣」不同——库存是公共资源需延迟扣减，券是用户私有资产，下单锁定无副作用，且完全对齐秒杀「抢购资格先占、超时释放」的既有语义。

### 3.3 券类型范围与是否引入 MQ

- **券类型**：本期仅实现**满减券**（无门槛 / 满 X 减 Y），字段预留 `coupon_type`（1=满减券，预留 2=折扣券），折扣券不作本期实现，避免计算口径复杂化。
- **MQ**：不引入。领取 / 核销均为单事务 10~20ms 量级，演示环境同步处理足够；与秒杀结论一致，答辩时口述"生产可加 MQ 异步化"。

### 3.4 成本量化（本方案新增资源）

| 项 | 量级 |
| --- | --- |
| 新增表 | 2 张（`coupon`、`user_coupon`），`order` 表加 2 列 + 1 普通索引 |
| Redis 内存 | 每张券 2 个 key（stock + 用户标记），约 300B；100 张券 < 50KB，可忽略 |
| 新依赖 | 0（复用 Redis / Hutool / 雪花ID） |
| 定时任务 | 1 个每日过期扫描（`CouponExpireScheduler`），与 `OrderTimeoutScheduler` 同款 |

## 4. 总体架构与流程

```
管理端 CouponListView ──► AdminCouponController ──► AdminCouponService ──► coupon 表
                                                                  │ 上下架/变更时写 Redis
                                                                  ▼
小程序 领券中心/我的券包 ──► CouponController ──► CouponService
                                                                  │ ① 领取：Lua 原子预扣(库存+防重)
                                                                  │ ② 生成 user_coupon(唯一索引兜底)
                                                                  ▼
结算页 confirm.vue ──► POST /order/create(couponId)
                                                                  │ ③ 校验归属/门槛/有效期/秒杀互斥
                                                                  │ ④ 条件 UPDATE 原子核销(status 0→1)
                                                                  │ ⑤ discount 落账 → payAmount = total + freight - discount
                                                                  ▼
                                                         order 表(coupon_id 非空)
                                                                  │
                                                  OrderTimeoutScheduler / cancelOrder
                                                                  │ 超时/手动取消 → 券状态回退(1→0)
                                                                  ▼
                                                         PaymentServiceImpl(零改动)
```

核心原则：**Redis 管「领取资格」，DB 管「核销与最终状态」**，两者最终一致；核销/回退均为条件 UPDATE，幂等可重入。

## 5. 数据库设计

### 5.1 新增表：`coupon`（券模板）

```sql
-- sql/coupon_module.sql

USE `agsell`;

DROP TABLE IF EXISTS `coupon`;
CREATE TABLE `coupon` (
    `id`             BIGINT        NOT NULL AUTO_INCREMENT COMMENT '主键',
    `coupon_name`    VARCHAR(50)   NOT NULL COMMENT '券名称（如：满99减10）',
    `coupon_type`    TINYINT       NOT NULL DEFAULT 1 COMMENT '券类型 1=满减券（本期仅此类型，预留2=折扣券）',
    `threshold`      DECIMAL(10,2) NOT NULL DEFAULT 0.00 COMMENT '使用门槛（订单满X元可用，0=无门槛）',
    `amount`         DECIMAL(10,2) NOT NULL COMMENT '优惠金额（满减面额）',
    `total_count`    INT           NOT NULL DEFAULT 0 COMMENT '发放总量（0=不限量）',
    `received_count` INT           NOT NULL DEFAULT 0 COMMENT '已领取数量（冗余计数，Redis 预热数据源）',
    `per_user_limit` INT           NOT NULL DEFAULT 1 COMMENT '每人限领数量（本期固定1）',
    `valid_days`     INT           NOT NULL DEFAULT 7 COMMENT '领取后有效天数（相对有效期，从领取时刻起算）',
    `start_time`     DATETIME      DEFAULT NULL COMMENT '领取开始时间（NULL=立即开始）',
    `end_time`       DATETIME      DEFAULT NULL COMMENT '领取结束时间（NULL=长期有效）',
    `status`         TINYINT       NOT NULL DEFAULT 1 COMMENT '状态 0=下架 1=上架',
    `sort`           INT           NOT NULL DEFAULT 0 COMMENT '排序值，越大越靠前',
    `create_time`    DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    `update_time`    DATETIME      DEFAULT NULL ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    `deleted`        TINYINT       NOT NULL DEFAULT 0 COMMENT '软删除标记',
    PRIMARY KEY (`id`),
    KEY `idx_status_sort` (`status`, `sort`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='优惠券模板表';
```

管理端建档校验规则（服务端强制）：

- `amount > 0`；
- `threshold >= 0`（无门槛券为 0），`threshold` 与 `amount` 无强制大小关系（下单时取 `min(amount, 订单金额)` 兜底）；
- `total_count >= 0`；`per_user_limit >= 1`（本期固定 1）；
- `valid_days >= 1`；若填领取起止时间则 `end_time > start_time`；
- `total_count > 0` 时必须 `received_count = 0`（新券初始）。

### 5.2 新增表：`user_coupon`（用户券）

```sql
DROP TABLE IF EXISTS `user_coupon`;
CREATE TABLE `user_coupon` (
    `id`           BIGINT        NOT NULL AUTO_INCREMENT COMMENT '主键',
    `user_id`      BIGINT        NOT NULL COMMENT '用户ID',
    `coupon_id`    BIGINT        NOT NULL COMMENT '券模板ID',
    `status`       TINYINT       NOT NULL DEFAULT 0 COMMENT '状态 0=未使用 1=已使用 2=已过期',
    `order_no`     VARCHAR(32)   DEFAULT NULL COMMENT '核销订单号（已使用时记录，对账用）',
    `use_time`     DATETIME      DEFAULT NULL COMMENT '核销时间',
    `expire_time`  DATETIME      NOT NULL COMMENT '该张券的过期时间（= 领取时间 + valid_days）',
    `receive_time` DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '领取时间',
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_user_coupon` (`user_id`, `coupon_id`),
    KEY `idx_user_status` (`user_id`, `status`),
    KEY `idx_expire` (`status`, `expire_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='用户优惠券表';
```

设计说明：

- **防重复领取**：`uk_user_coupon (user_id, coupon_id)` 唯一索引持久兜底。本期 `per_user_limit = 1`，天然成立；若后续放开每人多张，删除该唯一索引改为 Redis 计数即可（字段与逻辑已预留）。
- **过期判定双保险**：核销/展示时实时判断 `expire_time`（不依赖状态字段），同时定时任务把过期券批量置为 `status=2`（仅优化"我的券包"展示过滤）。
- **回退语义**：取消/超时回退 = `status` 1→0、清空 `order_no`/`use_time`，券回到未使用状态，有效期内可再次使用。

### 5.3 订单表扩展（`order`）

```sql
ALTER TABLE `order`
    ADD COLUMN `coupon_id` BIGINT DEFAULT NULL COMMENT '用户优惠券ID（user_coupon.id，非优惠订单为NULL）' AFTER `remark`,
    ADD COLUMN `coupon_name` VARCHAR(50) DEFAULT NULL COMMENT '优惠券名称（快照，券模板删除后仍可展示）' AFTER `coupon_id`,
    ADD KEY `idx_coupon_id` (`coupon_id`);
```

- 优惠金额**不新增字段**：直接落已有 `discount`（此前写死 0），金额口径统一为 `payAmount = totalAmount + freight - discount`；
- `coupon_name` 做快照：券模板软删/改名不影响历史订单展示；
- 普通订单 `coupon_id = NULL`，索引零影响（与 `seckill_activity_id` 同一扩展手法）。

## 6. 后端设计

### 6.1 Redis Key 设计

| Key | 类型 | 说明 | 过期策略 |
| --- | --- | --- | --- |
| `coupon:stock:{couponId}` | String(int) | 剩余可领数量（`total_count - received_count`，无限量券不建此 key） | 随券上下架/变更写入 |
| `coupon:user:{couponId}:{userId}` | String | 用户已领标记 `1` | 常驻（一人一张终身标记） |

> 预热时机：管理端创建 / 编辑 / 上下架时由管理端服务同步写 Redis；Redis 无缓存时领取请求查 DB 后回填，DB 为唯一事实来源（对齐秒杀快照策略）。

### 6.2 领取核心 Lua 脚本（防超发 + 防重复原子完成）

```lua
-- KEYS[1] = coupon:stock:{couponId}   （无限量券传占位 key，跳过库存段）
-- KEYS[2] = coupon:user:{couponId}:{userId}
-- ARGV[1] = userId
-- 返回：1=成功  0=已领完  -1=未初始化/不存在  -2=已领取过

if redis.call('EXISTS', KEYS[2]) == 1 then return -2 end

local stock = tonumber(redis.call('GET', KEYS[1]) or '-1')
if stock < 0 then return -1 end
if stock <= 0 then return 0 end

redis.call('DECR', KEYS[1])
redis.call('SET', KEYS[2], '1')
return 1
```

单次网络往返完成「查重 + 查库存 + 扣库存 + 标记」，无竞态窗口。**DB 层 `uk_user_coupon` 唯一索引兜底**：Lua 成功但 DB INSERT 失败（理论极端）时，回补 `INCR` 库存 + `DEL` 用户标记（与秒杀失败补偿同构）。

### 6.3 领取时序（`CouponService.receiveCoupon`）

```
1. 用户已登录（BaseContext）
2. 查券模板（DB → 无则不存在）
   ├─ deleted / status != 1        → COUPON_NOT_FOUND
   ├─ start_time > now             → COUPON_RECEIVE_END
   ├─ end_time < now               → COUPON_RECEIVE_END
   └─ 通过
3. 执行 Lua 原子扣减
   ├─ 返回 0  → COUPON_SOLD_OUT
   ├─ 返回 -2 → COUPON_RECEIVE_REPEAT
   └─ 返回 -1 → DB 直查兜底（限量校验 received_count < total_count），仍失败 → SYSTEM_ERROR
4. 构建 user_coupon：
   status=0、expire_time = now + valid_days
5. INSERT user_coupon（事务）
   └─ 唯一索引冲突 → COUPON_RECEIVE_REPEAT（回补 Redis，见 6.2）
6. 更新 coupon.received_count = received_count + 1
7. 返回券信息（含 expire_time）
```

### 6.4 下单核销时序（`OrderServiceImpl.createOrder` 改造）

在现有「计算总金额 → 计算运费」之间插入优惠券核销段（金额计算仍以服务端为准）：

```
1. request.couponId 为空 → 跳过（普通流程不变）
2. 秒杀互斥防御：该请求若命中秒杀单上下文 → COUPON_SECKILL_FORBIDDEN
   （秒杀走独立入口天然不带 couponId，此为防御性校验）
3. 查 user_coupon（id + userId 归属）
   ├─ 不存在 / status != 0 / expire_time < now → COUPON_INVALID
4. 校验门槛：totalAmount >= threshold，否则 COUPON_THRESHOLD_NOT_MET
5. 原子核销（条件 UPDATE，防并发双花）：
   UPDATE user_coupon SET status=1, order_no=?, use_time=NOW()
   WHERE id=? AND user_id=? AND status=0
   └─ 影响行数 = 0 → COUPON_INVALID（已被他用/已过期）
6. discount = min(amount, totalAmount)   -- 面额兜底，永不超订单金额
7. payAmount = totalAmount + freight - discount
8. order.coupon_id / coupon_name 落库（快照）
```

> **事务边界**：核销与订单创建在同一 `@Transactional` 内。若后续插入订单失败，事务回滚，券核销状态一并回滚，无需补偿代码（与秒杀"下单失败回补 Redis"的差异点：秒杀名额在 Redis，需显式补偿；券状态在 DB 事务内，自动回滚）。

### 6.5 券回退（闭环，幂等）

触发点两处，均使用条件 UPDATE 保证幂等（`WHERE id=? AND status=1 AND order_no=?`，重复取消不重复回退）：

| 触发 | 位置 | 动作 |
| --- | --- | --- |
| 订单超时自动取消 | `OrderServiceImpl.cancelExpiredOrders` 改造 | `user_coupon` 1→0、清空 `order_no`/`use_time` |
| 用户手动取消 | `OrderServiceImpl.cancelOrder` | 同上 |

改造说明：两处与秒杀释放 `releaseSeckillQuota` 并列挂载——取消待付款订单时，`seckill_activity_id` 非空走秒杀释放，`coupon_id` 非空走券回退，互不干扰。

### 6.6 过期批处理（`CouponExpireScheduler`）

- 复用 `OrderTimeoutScheduler` 的 `@Scheduled` 模式，每日 03:00 执行；
- `UPDATE user_coupon SET status=2 WHERE status=0 AND expire_time < NOW()`（批量，限 1000 条/批）；
- 展示与核销仍实时校验 `expire_time`，定时任务仅做状态收敛，不承担正确性。

### 6.7 接口清单

**管理端 `/api/admin/coupon`（需管理员 JWT）**

| 方法 | 路径 | 说明 |
| --- | --- | --- |

## 11. 风险与边界

| 风险 | 应对 |
| --- | --- |
| Redis 宕机无法领取 | 领取走 DB 直查兜底（received_count < total_count 校验），不静默超发；`uk_user_coupon` 唯一索引最终防重复 |

## 12. 答辩问题预演（Q&A）

**Q：如何防止优惠券被超发？**

A：双保险。领取时 Redis Lua 原子脚本"查重→查库存→DECR→标记"单次往返完成；即使 Redis 异常降级到 DB，`received_count < total_count` 条件更新兜底，最终 `coupon` 表已领取数不超总量。

**Q：如何防止一个人领多张？**

A：Redis `SETNX` 用户标记毫秒级预检 + `user_coupon` 表 `(user_id, coupon_id)` 唯一索引持久兜底，与秒杀一人一单同构。

**Q：用户下单用了券但不付款怎么办？**

A：券在下单时原子核销锁定，订单取消或 30 分钟超时自动取消时，券状态条件回退为未使用，有效期内可再次使用——与秒杀"抢购资格超时释放"同一闭环。

**Q：同一张券能同时用在两个订单吗？**

A：不能。核销是 `UPDATE user_coupon SET status=1 WHERE status=0` 的条件更新，第二个订单必然影响行数为 0 而被拒绝。

**Q：为什么核销放在下单而不是支付成功？**

A：券是用户私有资产，下单锁定无副作用，还能保证结算金额确定；放在支付成功则需要处理"两个待付款订单抢同一张券"的支付期冲突，复杂度高。库存是公共资源才需要延迟到支付扣减，两者资源性质不同。

**Q：优惠券能和秒杀叠加吗？**

A：不能。秒杀走独立下单入口，天然不带券；`createOrder` 再做防御性拦截，保证双重优惠不会叠加。

## 13. 券类型扩展：折扣券 + 品类券（v1.1 增补）

> 本节为二期扩展。一期仅满减券（`coupon_type=1`），本节新增**折扣券（2）**与**品类券（3）**。
> **设计原则**：领取 / 扣库存 / 过期 / 回退等生命周期逻辑**完全复用一期**，仅"可用性判断 + 金额计算"两处按类型分支扩展，不破坏一期已联调通过的链路。

### 13.1 类型编号与字段语义

| coupon_type | 类型 | 使用门槛 threshold | 优惠字段 | 商品范围 | 说明 |
| --- | --- | --- | --- | --- | --- |
| 1 | 满减券（一期） | 满 X 元 | `amount`（减 Y 元） | 全店通用 | 现状不变 |
| 2 | 折扣券 | 满 X 元（0=无门槛） | `discount`（折扣率）+ `max_discount`（封顶） | 全店通用 | 如 0.85 = 85 折，最多减 `max_discount` |
| 3 | 品类满减券 | 满 X 元 | `amount`（减 Y 元） | **仅限指定商品** | 关联 `coupon_product`，订单商品须全部命中 |

- 折扣率 `discount`：存小数（0.01~0.99），`0.85` 即付 85%、减 15%；前端展示时 ×10 显示"8.5 折"。
- `max_discount = 0` 表示不封顶（折扣额 = 订单金额 × (1 − discount)）；>0 时优惠额不超过该值。
- 一期满减券的 `amount` 语义不变；折扣券 `amount` 字段不用（建券时不填），品类券复用 `amount`。

### 13.2 表结构变更（`sql/coupon_type_extension.sql`）

**coupon 表加两列**：

```sql
ALTER TABLE `coupon`
    ADD COLUMN `discount`     DECIMAL(3,2)  DEFAULT NULL COMMENT '折扣率（仅折扣券，0.85=85折）' AFTER `amount`,
    ADD COLUMN `max_discount`  DECIMAL(10,2) DEFAULT NULL COMMENT '折扣封顶金额（仅折扣券，0/NULL=不封顶）' AFTER `discount`;
```

**新增品类券商品关联表**：

```sql
DROP TABLE IF EXISTS `coupon_product`;
CREATE TABLE `coupon_product` (
    `id`         BIGINT      NOT NULL AUTO_INCREMENT COMMENT '主键',
    `coupon_id`  BIGINT      NOT NULL COMMENT '券模板ID',
    `product_id` BIGINT      NOT NULL COMMENT '商品ID',
    `create_time` DATETIME   NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_coupon_product` (`coupon_id`, `product_id`),
    KEY `idx_product` (`product_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='品类券适用商品关联表';
```

- `uk_coupon_product` 防重复挂商品；
- 品类券删除 / 编辑商品范围时，先清该券的关联行再重插（事务内）；
- 满减券、折扣券**不写** `coupon_product`，关联表为空即代表全店通用。

建券校验规则（服务端强制，按类型分支）：

- 满减券（1）：`amount > 0`；`threshold >= 0`；
- 折扣券（2）：`discount` 必须在 (0, 1) 开区间（0.01~0.99）；`max_discount` 可空/0；`amount` 忽略；
- 品类券（3）：`amount > 0`；`threshold >= 0`；**必须挂载至少 1 个商品**（空关联表拒绝保存）。

### 13.3 计算规则（`CouponCalculator` 重构为策略分支）

一期 `calculate(coupon, totalAmount)` 只能算满减，重构为按类型分派：

```
入参：coupon（模板）、totalAmount（订单商品总金额）、orderItems（订单商品ID集合，品类券校验用）

1. 门槛校验：totalAmount < threshold  → 不可用（THRESHOLD_NOT_MET）
2. 商品范围校验（仅 type=3 品类券）：
   取 coupon_product 中该券的 productId 集合 scope
   订单任一 orderItems.productId ∉ scope  → 不可用（SCOPE_NOT_MET）
3. 按类型算优惠额 discountAmount：
   ├─ type=1 满减：min(amount, totalAmount)
   ├─ type=2 折扣：raw = totalAmount × (1 − discount)
   │                discountAmount = max_discount > 0 ? min(raw, max_discount) : raw
   │                （兜底不超过 totalAmount）
   └─ type=3 品类：min(amount, totalAmount)   -- 金额口径同满减
4. 返回 discountAmount（永远 >=0，且 <= totalAmount）
```

**金额口径不变**：`payAmount = totalAmount + freight − discountAmount`，与一期一致；折扣券只是 `discountAmount` 的算法不同，落库字段仍是 `order.discount`。
