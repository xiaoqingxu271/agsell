# 基于 RAG 与大模型智能体的农产品电商智能导购系统的设计与实现

> 本科毕业设计论文初稿（供作者删改、排版使用；图表以占位说明标注，实验数据均引自 `doc/量化实验报告.md` 与 `ai-service/scripts/eval_results/` 存档）

## 摘　要

农产品电商在快速发展的同时，面临商品信息不对称、消费者决策成本高、在线客服人力成本上升等现实问题。传统关键词检索与规则客服难以理解用户以自然语言表达的模糊需求，也无法在经营知识与业务数据之间建立可核查的关联。本文设计并实现了一个基于检索增强生成（Retrieval-Augmented Generation，RAG）与大模型智能体的农产品电商智能导购系统。系统采用三端一体架构：以 Spring Boot 为核心的交易后端、Vue 3 管理后台、uni-app 双端用户端，以及一个独立的 Python AI 服务；AI 服务以 LangGraph 状态图编排大模型智能体，将知识问答、业务查询与商品导购统一到"检索—取证—作答"一条链路上。针对大模型幻觉问题，本文设计了三路混合召回（bge 向量 + MySQL ngram 全文 BM25 + 关键词）线性加权融合与 bge-reranker 交叉编码重排相结合的检索链路，并以阈值闸门、确认带与词面校验构成双道反幻觉闸门；针对复杂诉求，实现了基于 function calling 的有界 ReAct 工具编排（步数上限、调用数上限、调用去重、空结果反思重试与能力协商降级），并设计了五级证据链导购通道与六路信号个性化重排。量化实验表明：知识库主口径检索 Hit@1 达 97.2%、MRR 0.986，域外问题拒答率 100%，智能体工具选择准确率 86.2%（规则通道同批仅 37.6%），高并发秒杀场景零超卖。系统实现了从浏览、下单到售后的完整购物闭环，验证了 RAG 与大模型智能体在垂直电商导购场景中的工程可行性。

**关键词**：检索增强生成；大模型智能体；智能导购；农产品电商；混合检索；LangGraph

## Abstract

Along with the rapid development of agricultural e-commerce, problems such as information asymmetry, high decision-making costs for consumers and rising labor costs of online customer service have become prominent. Keyword-based retrieval and rule-based chatbots can hardly understand vague natural-language demands, nor can they build verifiable links between business knowledge and transaction data. This thesis designs and implements an intelligent shopping-guide system for agricultural e-commerce based on Retrieval-Augmented Generation (RAG) and LLM-based agents. The system adopts a three-end architecture: a Spring Boot transaction backend, a Vue 3 admin console, a uni-app client, and an independent Python AI service. The AI service orchestrates an LLM agent with a LangGraph state graph, unifying knowledge QA, business data query and product recommendation into one "retrieve—gather—answer" pipeline. To suppress hallucination, a hybrid retrieval pipeline is built with three-lane recall (bge vectors, MySQL ngram full-text BM25, and keywords) fused by linear weighting and re-ranked by a bge-reranker cross-encoder, guarded by threshold gates, a confirmation band and lexical verification. For complex demands, a bounded ReAct tool-planning loop based on function calling is implemented with step/call limits, deduplication, reflection retry and capability negotiation. Experiments show that the retrieval Hit@1 reaches 97.2% (MRR 0.986), the out-of-domain refusal rate is 100%, the agent tool-selection accuracy is 86.2% (versus 37.6% for the rule channel), and zero overselling is achieved under high-concurrency seckill. The results verify the engineering feasibility of RAG and LLM agents in vertical e-commerce guide scenarios.

**Key words**: Retrieval-Augmented Generation; LLM agent; intelligent shopping guide; agricultural e-commerce; hybrid retrieval; LangGraph

# 1　绪论

## 1.1　研究背景与意义

在乡村振兴战略持续推进与数字经济加速渗透的背景下，农产品上行——即农产品经由电商平台从产地直达城市消费者——已经成为促进农民增收、缩短流通链条的重要途径。中国互联网络发展状况统计报告显示，我国网络购物用户规模已超过 9 亿，农产品网络零售额持续增长，电商平台成为农产品流通体系中的关键基础设施[17]。学术界对生鲜农产品电商的研究也表明，电子商务能够通过压缩中间环节、重构信息流与信任机制，缓解生鲜农产品"卖难买贵"的流通困局[18]。

然而，农产品电商在用户体验侧仍存在若干突出问题。其一，农产品是非标准化商品，产地、时令、储存方式、食用场景等属性高度多样，消费者在"挑什么、怎么挑"上决策成本高：普通搜索只能匹配用户输入的字面关键词，而"过年走亲戚拎点什么体面""给小宝宝做辅食买什么"这类真实问法并不包含品类词，关键词检索无法给出有效结果。其二，平台规则（运费、退换货、发货时限）、订单状态、物流进度等知识分散在商品详情、政策文档与业务数据库中，用户需要自行查找或等待人工客服，而人工客服人力成本高、响应不及时。其三，通用大语言模型虽然具备强大的自然语言理解与生成能力，但直接用于垂直电商场景存在幻觉风险：模型可能编造平台不存在的优惠政策、虚构商品口碑，甚至对经营范围之外的请求强行给出"看似合理"的答案，这对以信任为核心的农产品交易场景是不可接受的。

检索增强生成（RAG）通过在生成前从外部知识库检索证据、将证据注入上下文，使大模型的回答有据可依，是缓解幻觉的主流范式[3]。大模型智能体（LLM Agent）则进一步让模型通过调用工具与外部环境交互，自主完成多步骤任务[13,14,15]。将 RAG 与智能体技术引入农产品电商导购，有望以较低的人力成本实现"问得懂、查得到、答得准、可核查"的智能客服与导购体验。本文即以此为出发点，设计并实现了一套将 RAG 知识问答、私有业务数据查询与个性化商品导购统一在一条对话链路上的智能导购系统，并围绕反幻觉、有界编排、检索质量与响应延迟等关键问题给出工程化的解决方案与量化验证。研究的意义在于：一方面为垂直电商场景落地 RAG 与智能体技术提供了一套经过实验检验的架构与阈值选型依据；另一方面结合农产品溯源、时令新鲜度等行业特性，探索了大模型技术与农产品电商结合的具体形态。

## 1.2　国内外研究现状

### 1.2.1　检索增强生成（RAG）

RAG 由 Lewis 等人于 2020 年提出，其核心思想是将参数化知识（模型权重）与非参数化知识（外部语料库）结合：生成答案前先用检索模型从语料库中召回相关文档，再将文档作为上下文交给生成模型，从而显著提升知识密集型任务的事实准确性[3]。在检索侧，Karpukhin 等提出的稠密段落检索（DPR）以双编码器结构独立编码问题与段落、以向量内积衡量相关度，成为开放域问答检索的主流方案[4]；中文场景下，北京智源人工智能研究院发布的 BGE（BAAI General Embedding）系列模型在中文语义检索基准上表现优异，是当前中文 RAG 应用的事实标准之一[8]。针对稠密检索对精确词面匹配不敏感的问题，工业界普遍采用稠密向量与稀疏检索（如 BM25[5]）并用的混合检索（hybrid search），再通过倒数排序融合（RRF）[6]或线性加权等策略合并两路结果；Cormack 等的实验表明 RRF 在无调参条件下优于单路排序[6]，但其基于排名的融合会丢失分数距离信息，在特定分布下并非最优，本文在实验中也观察到了这一现象（见第 6 章）。为弥合"召回—精排"之间的差距，Nogueira 等将查询与文档拼接后送入 BERT 交叉编码器打分的重排方法[10]被广泛采用，BGE-Reranker 即是该思路在中文场景的工程化实现[9]。在 RAG 评估方面，除命中率、MRR 等检索层指标外，近年来出现了以 RAGAS 为代表的生成层自动评估框架，从忠实度（faithfulness）与相关性（relevance）等维度度量回答对证据的贴合程度[16]。

### 1.2.2　大模型智能体与工具编排

以 Transformer 为基础的预训练语言模型[1,2]经过指令微调与人类反馈对齐后，具备了遵循复杂指令的能力[14]。让模型调用外部工具是突破其固有限制（知识时效、私有数据访问、精确计算）的直接途径：Schick 等提出的 Toolformer 证明了模型可以自学何时、如何调用 API[12]；Yao 等提出的 ReAct 范式将推理（Reasoning）与行动（Acting）交替进行，使模型在"思考—行动—观察"的循环中逐步完成任务，成为当前工具型智能体的代表性方法[11]。在工程框架层面，LangGraph 以状态图（StateGraph）为抽象，将智能体建模为节点与条件边的组合，原生支持循环、分支、持久化检查点（checkpointer）与人工介入，已成为构建生产级智能体应用的主流编排框架之一[13,15]。与把决策完全交给模型的"无限循环 ReAct"相比，生产环境更关注有界性（boundedness）：通过限制推理步数、工具调用次数与重复调用，约束最坏情况下的延迟与成本，这在本系统的免费大模型网关（单次规划 6~15 秒）条件下尤为关键。

### 1.2.3　农产品电商与智能导购

农产品电商研究早期聚焦于流通渠道与模式创新，如汪旭晖等通过双案例比较揭示了电子商务破解生鲜农产品流通困局的内在机理[18]；随着基础设施成熟，研究重心逐步转向消费者信任（溯源体系）、品牌化与数字化运营。在智能导购方面，主流电商平台的推荐系统以协同过滤与深度学习排序模型为主，其作用位置在"信息流分发"，对会话式、解释性的购物咨询支持有限。近年来部分平台上线了大模型驱动的购物助手，但公开资料中针对垂直农产品场景、同时覆盖"知识问答 + 私有数据查询 + 导购推荐"三类诉求、并以反幻觉为一等约束的完整工程方案与量化实验仍较少。农产品场景的特殊性——商品属性（产地、保质期、储存方式）天然适合作为可核查的"证据"、溯源数据天然适合作为知识库语料、经营范围边界清晰天然适合做域外拒答——恰恰为 RAG 与智能体提供了理想的试验场，这是本文工作的切入点。

# 2　相关技术

## 2.1　检索增强生成（RAG）

RAG 的基本流程分为离线索引与在线检索两个阶段。离线阶段将知识源（FAQ 条目、文档、数据库记录）切分为适合检索的文本块（chunk），经嵌入模型（Embedding Model）编码为稠密向量后写入向量数据库；在线阶段将用户查询同样编码为向量，通过相似度计算（如余弦相似度）召回 Top-K 相关文本块，与查询一起组装进提示词（prompt），交由大语言模型生成最终回答[3]。RAG 的价值在于：知识更新无需重训模型、回答可溯源到具体条目、私有数据不必进入模型训练过程，这三点分别对应本系统的"运营即时生效""依据标签"与"隐私最小化"需求。

嵌入模型选用 BAAI/bge-small-zh-v1.5[8]。该模型是面向中文优化的双向编码器表示模型，512 维输出，约 95 MB，通过 ONNX Runtime 本地推理，CPU 毫秒级延迟，无需 GPU 与 torch 依赖，适合轻量部署；其在 512 token 内的上下文长度也约束了切块粒度的上限（见 5.2 节）。交叉编码重排采用 BGE-Reranker[9]：与双编码器独立编码不同，交叉编码器将（查询， 文档）对拼接后共同过编码器，逐对输出相关度分值，因能建模词项级交互而判别力显著更强[10]，代价是每对都要做一次前向计算，故只用于对召回池（本系统取 20 条）精排而非全库检索。

## 2.2　混合检索与融合排序

单一检索通道各有盲区：稠密向量检索擅长同义改写（"不想要了能退吗"≈"退货政策"），但对未见过的专有名词与精确词面匹配偏弱；BM25 等稀疏检索[5]擅长关键词精确命中，但无法跨越词面差异。混合检索并行运行多路召回，再融合排序。常见融合策略有二：一是 RRF，按各通道内的排名倒数累加得分，优点是无需调参、量纲无关[7]；二是线性加权，将各通道分数归一后加权求和，保留了分数的绝对差异信息。本文的实现对比了两种策略，实测 RRF 在本系统数据分布上会压缩"两路排名相同但语义强弱不同"的条目之间的分差，导致 Hit@1 退化（详见 6.3 节），最终采用线性加权融合。

## 2.3　大模型智能体与 LangGraph

大模型智能体是以大语言模型为核心决策器、能够感知环境、调用工具并迭代完成任务的软件系统[13]。function calling 机制允许开发者将能力描述为 JSON Schema 形式的函数目录，由模型在对话中输出结构化的工具调用请求，应用侧执行后将结果回灌，模型再决定下一步动作，这一"规划—执行—观察"循环即 ReAct 范式的工程化[11,12]。

LangGraph 在 LangChain 生态之上提供状态图编排能力[15]：节点（node）是接收并返回状态的函数，边（edge）与条件边（conditional edge）刻画控制流，状态（State）以类型化字段在图中流转，检查器（checkpointer）将状态按会话线程（thread_id）持久化，从而天然支持多轮记忆、断点恢复与流式输出。本系统以 LangGraph 构建客服智能体，图结构为 `START → intent →（smalltalk | human_fallback | agent → generate）→ END`，其中 agent 节点内部实现有界 ReAct 循环（见 4.2 节）。与"意图分类 argmax → 固定单分支"的旧式工作流相比，工具编排将"调用什么"的决策权交给模型，天然支持一句话多诉求的并行取证；同时为控制免费网关下的延迟与额度消耗，必须以步数上限、调用数上限与去重机制对循环做硬性封顶。

## 2.4　工程支撑技术

**Spring Boot 与 MyBatis-Plus**：交易后端以 Spring Boot 4.1.1（JDK 21）构建，MyBatis-Plus 3.5.15 提供 ORM 与通用 CRUD，自研 JWT 拦截器实现无状态认证与角色控制，Redis 承担登录令牌、秒杀库存与限流计数，MySQL 8 为持久层，Knife4j 生成 OpenAPI 文档。

**Vue 3 与 Element Plus**：管理后台采用 Vue 3 组合式 API + Element Plus 组件库 + Pinia 状态管理 + ECharts 可视化 + Vite 构建，共 17 个功能页，含 AI 知识库维护与转人工工单两个 AI 运营页面。

**uni-app 跨端框架**：用户端以 uni-app（Vue 3 语法）实现一套代码编译微信小程序与 H5 双端，共 28 个页面；小程序端自研 SSE（Server-Sent Events）解析器承接 AI 回复的流式逐字下发。

**FastAPI 与 SQLAlchemy**：AI 服务以 FastAPI 构建，Pydantic v2 做请求校验，SQLAlchemy + PyMySQL 以只读方式访问业务库（写仅限 AI 知识库表），httpx 异步回调 Java 内部接口。

**向量数据库 Chroma**：采用进程内持久化的 Chroma 存储知识库与商品两个向量集合（collection），余弦距离，零部署成本，索引可全量重建，符合本系统万条以下规模的轻量场景。

# 3　需求分析

## 3.2　功能性需求

用户端功能需求覆盖完整购物链路：首页运营位（轮播、分类入口、热销、新品、限时特惠）、分类浏览、搜索（关键词 + 语义召回 + 热词/高亮）、商品详情（口碑摘要条：好评率与好评关键词）、收藏、购物车、下单结算（运费预览、优惠券核销）、模拟支付、订单状态机（待付款→待发货→待收货→已完成，超时自动取消）、评价（带情感标签）、售后退款、优惠券领取与核销、秒杀、产地溯源（扫码查看生产记录）、消息中心（发货/售后站内信）与 AI 智能客服。

管理端功能需求覆盖 17 个功能页，其中与 AI 直接相关的有三个：知识库维护（FAQ 增删改查即时同步向量索引、索引状态四数卡、近 7 日被引用 Top、AI 运营统计）、AI 运营配置（检索条数、闸门阈值、重排开关、编排上限等后台可调立即生效）与转人工工单处理（待处理排前、原子抢占防重复处理）。

AI 客服的功能需求是本系统的核心，按题目三个关键词归纳：

1. **知识问答（RAG）**：运费、退换货、支付、秒杀、溯源等平台规则与商品知识问题，只能依据知识库条目回答；命中条目以"依据"引用标签结构化展示；检索零命中或低于阈值时输出确定性拒答话术，不经大模型。
2. **业务查询（智能体工具）**：订单、物流、售后进度等用户私有数据，必须由智能体经服务端回调 Java 取数，强制归属校验，不接受用户口述单号以外的来源；未登录时引导登录而非报错。
3. **智能导购**：理解"有没有适合减脂期吃的粗粮"这类自然语言需求，语义召回在售商品并按用户偏好重排，结果以可点击商品卡片呈现且卡片先于文字到达；推荐理由只用商品真实字段，零评价商品显示"暂无评价数据"。

三类能力的共同约束是**反幻觉**：没有依据就不编造，宁可拒答并引导人工，也不能给出看似合理的假答案。

## 3.3　非功能性需求

**性能**：常规 API 平均响应时间 ≤ 500 ms；AI 侧因依赖大模型网关，以"首 token 延迟"为体验指标，寒暄类 2~3 s、FAQ 类约 9.6 s、导购类约 10.5 s（实测值，见 6.4 节），取证阶段完成即先下发商品卡以缩短感知等待。**安全性**：密码 BCrypt 加密；JWT 24 小时有效期且用户端/管理端 token 分型隔离；服务间调用以独立 `X-Internal-Key` 鉴权且未配置即拒绝（fail-closed）；AI 返回的订单 VO 刻意剔除收货人、电话、地址字段；AI 相关端点按调用主体限流。**可用性与降级**：大模型限流/超时、Java 或向量库不可用时，用户只看到友好话术，不出现"系统错误"等内部文案；检索层任一通道故障自动退场，不因单通道故障对用户报错。**可维护性**：数据库变更以增量迁移脚本管理；依赖版本以锁文件固定（AI 侧 139 包）；每个实验存档带时间戳与代码版本（provenance）。

### 4.2.1　智能体编排的状态图设计

图结构为 `START → intent →（smalltalk | human_fallback | agent → generate）→ END`。各节点职责如下：

- **intent（规则前置）**：只做高置信、零成本、不需要取数的判断——转人工强诉求与纯寒暄两类在此定案，分别路由至 human_fallback 与 smalltalk 节点，不消耗大模型调用；其余请求一律进入 agent 节点。该节点同时负责每轮开始时重置上一轮的工具产物与观察（observations 等临时状态），防止跨轮复述上一轮隐私。之所以将规则层限定在这两类，是因为消融实验证明词表规则不能承担语义分类职责（hold-out 集上仅 37.6%，见 6.5 节），但"我要投诉/找真人"与"你好/谢谢"这类高置信判断恰好是它毫秒级、零成本的优势位置。
- **agent（有界工具编排）**：通过 `llm.bind_tools()` 将 6 个能力的 function schema 交给模型规划，一轮可并行发出多个工具调用；规划时注入最近 6 轮会话历史用于指代补全。循环受四重约束封顶：步数上限 `AGENT_MAX_STEPS=2`、单轮调用数上限 `AGENT_MAX_TOOL_CALLS=4`、按 (工具, 参数) 去重（重复调用不再执行、只回灌"已查过"提示）、提前退出（本步资料全部可用即停止，不再多花一次规划往返）。工具返回空结果或错误时，将摘要观察回灌并允许模型改写检索表述重试一次；出现多诉求（连接词/句读确定性计数）而取证次数不足时，跳过提前退出进入"补齐核对轮"。
- **generate（作答）**：唯一面向用户的文字出口。按确定性优先级依次检查五类不经大模型的出口——转人工话术、域外拒答、未登录引导、取数故障降级、知识库未覆盖拒答——只有当本轮确实取到 `status=ok` 的资料时，才将全部观察合并交给大模型组织回复；仅有商品浏览上下文时改走商品事实问答提示词。规划器的 tool_calls 与空回复一律不进 token 流，中间过程不外显。

规划、执行、作答三节点分离是本轮架构的关键取舍。实测发现模型拿到工具结果后可能不收敛（再发一遍同样的调用），因此"何时结束"由步数上限决定而非依赖模型自觉，最终回复由独立的 generate 节点基于观察组织，切断了"不收敛"影响回答质量的路径。

### 4.2.2　RAG 检索链路设计

检索链路如图 4-3 所示。

**图 4-3　RAG 检索链路（此处插入流程图，要素包括：**查询预处理（停用词表）→ 三路并行召回：① Chroma 向量通道（bge-small-zh，阈值闸门 KB_SCORE_THRESHOLD=0.5）② MySQL ngram 全文通道（BM25 相关度 + 词面校验）③ 关键词通道（ai_faq.keywords 子串，每命中 +0.5，封顶 3 个）→ 确认带裁决（向量分 ∈ [0.5, 0.6) 的商品域条目须词面佐证）→ 线性加权融合（向量原分 + 关键词 0.5/个 + 全文 0.3×归一相关度）→ bge-reranker 交叉编码重排（20 候选 → Top-5，失败回退融合序）→ 输出（条目 + references 引用标签）。**标注：**任一通道故障自动退场；重排只调整已过闸门条目先后、不放行新条目。**）**

知识库以 MySQL `ai_faq` 表为唯一数据源，向量索引为派生物、可随时全量重建。知识来源有四类：36 条平台规则类种子 FAQ、202 条商品知识（每个在售商品 1 条）、42 条类目知识、以及由溯源数据（生产记录/溯源档案）按句子边界 180/30 切块入库的 `trace_knowledge` 条目；另有管理端文档上传链路（txt/md/docx/pdf 抽文本后按 320/60 切块入库为 `doc_knowledge`，见 5.2 节）。扩容后知识库共 280 条评测覆盖条目（另有文档切块条目按来源整批管理）。

闸门体系是检索链路的反幻觉核心，由三部分构成：

1. **阈值闸门**：向量分低于 0.5 的条目不进入向量通道；全部命中为空时由生成节点输出确定性拒答话术。0.5 的选点依据是域内外可分性实测：域内查询 top-1 相似度均值 0.710，域外仅 0.375。
2. **确认带**：向量分落在 [0.5, 0.6) 的商品域条目（product_knowledge / category_knowledge / trace_knowledge）必须有词面佐证才能进入结果。设立原因是实测发现域内 top-1 最低 0.557 与域外最高 0.596 区间重叠、单阈值不可分，而唯一泄漏样本（"现在油价多少"命中食用油类目条目）恰是商品域条目；平台规则条目在带内实测 10/10 正确，无需加验。
3. **词面校验**：全文与关键词通道的命中必须通过"去掉停用词后的查询片段（≥2 字）出现在条目问句+答案原文中"的校验——"推荐一部电影"剥掉"推荐"后余下片段几乎不可能出现在知识库原文中，从而保证域外问法不会经由词面通道回流入答案。

### 4.2.3　智能导购与个性化重排设计

商品导购采用五级证据链通道，顺序即证据强度：

- **第 0 级　商详指代**：从商品详情页进线且模型未点出品类词时，判定用户问的就是眼前这件商品，只出该商品卡片并按其事实作答。设立该级的原因是指代句与真品类问句的向量分完全重叠（"这个能放多久？怎么保存"top-1 0.518 / "哪种茶叶比较好"0.558），调阈值无法区分，判据必须是结构性的（有无 productId + 有无 keyword）。
- **第 1 级　品类词 LIKE**：模型给出的品类词在商品名/副标题中真有命中是最硬证据，命中组在重排后仍置顶；LIKE 成类命中（≥2 条）时优先采信，不再让语义召回混入无关品。
- **第 2 级　语义召回**：对"适合送礼的柑橘"这类说不成品类的描述性需求，以独立闸门 `REC_MIN_SCORE=0.47` 召回候选并补齐 LIKE 的单薄结果（LIKE 命中组重排后仍置顶）。0.47 的选点来自阈值-风险曲线：0.35 时域外泄漏率 60%，0.47 处泄漏率降至 0% 而域内召回保持 90%（见 6.6 节）。搜索框沿用 0.35——搜索场景空结果可优雅退回 MySQL 全文检索，语义本来就与对话导购不同，两阈值不可混用。
- **第 3 级　域外拒答**：两路皆空且模型判定请求不属于经营范围（`inDomain=false`，schema 必填）时，输出确定性拒答话术，不经大模型、不降级热销榜。
- **第 4 级　热销兜底**：未拿到经营域判定（模型故障走兜底）时不拒答，行为与改造前一致，避免把反幻觉做成新的故障源。

个性化重排对登录用户叠加六路类目偏好信号（各路归一后按权重加权）：订单 0.5（已验证的真实选择）、收藏 0.35（显式强意向）、好评 0.3、加购 0.3、浏览 0.2（3 天半衰期时间衰减）、搜索词 0.15（关键词 LIKE 在售商品名映射品类，近 7 天窗口）。最终排序公式为：

> final = 语义分 + 0.25×类目偏好 + 0.10×销量归一 + 0.10×好评率 + 0.15×新鲜度

其中销量按全库在售最大销量做对数归一（固定基准，与候选集无关）；好评率取贝叶斯收缩值（先验 2 条虚拟评价）——在售 202 件商品中仅 7 件有已分析评价，直接用原始好评率会让"1 条差评"与"零评价"都被判为差商品；新鲜度按采摘日期与保质期计算 0~1 分（农产品特色项）。该打分函数是首页 feed、搜索框语义召回与对话导购三条链路的**唯一实现**：入口差异只体现在"有没有语义分"（首页 feed 无查询、语义项恒 0），权重与量纲完全一致，从架构上排除了"同一件商品换个入口名次就变"的问题。每个分项同时输出原始信号值与加权贡献值，前端可解释理由标签（如"时令""销量高""含'脐橙'关键词"）与服务端打分同源；口碑先验值参与排序但被 `rate_conf` 标记抑制，零评价商品不对外输出"好评率高"类理由。

### 4.2.4　会话记忆与多轮上下文

会话状态由 LangGraph checkpointer 按 thread_id（= sessionId）持久化，默认使用 SqliteSaver 落盘本地文件——选择原因是官方 RedisSaver 要求 Redis 8+ 内置 RediSearch，部署环境 Redis 5 不满足，而 SqliteSaver 同样达成跨重启恢复且零外部依赖（实测"我叫小明"→重启服务→"我是谁"能答对）。长会话按 3000 字符预算做历史窗口截断（`trim_messages`：system 常驻、保留最近对话、从完整人类轮次开始），控制长会话的 token 成本与首 token 延迟。多轮追问的召回串由执行器级规则改写兜底：最后一条消息较短（≤12 字）或含指代/追加词面特征（"这个""有没有""换个""便宜"等）时，自动拼接上一条用户消息作为召回上下文，零大模型成本地缓解"有没有便宜点的"这类丢约束追问；规划器则明确要求结合最近历史补全指代后改写检索句。

## 4.4　接口设计

服务间与对外接口遵循统一响应结构 `{code, message, data}`，业务状态码枚举化（0 成功、40000 参数错误、40100 未登录、40400 数据不存在/越权脱敏、50012 已抢光等）。本节仅说明 AI 相关的关键接口契约。

### 4.4.1　服务间鉴权与内部回调

Java 与 Python 之间全部调用以 `X-Internal-Key` 请求头鉴权，密钥由环境变量注入，两侧代码均无默认值——未配置即一律拒绝（fail-closed），不因"本地没配"而放行。Python 回调 Java 的内部接口如表 4-3 所示。

**表 4-3　AI 内部回调接口（Java 侧 `/api/ai/internal/**`）**

| 接口 | 请求体 | 说明 |
|---|---|---|
| POST /order/list | `{userId}` | 最近订单（按 JWT 解出的 userId 过滤） |
| POST /order/detail | `{userId, orderNo}` | 订单详情+物流，强制归属校验，他人订单 40400 |
| POST /after-sales/list | `{userId}` | 最近售后记录 |

返回给 AI 的订单 VO 刻意不含收货人、电话、地址字段（隐私最小化），即使模型被注入诱导，上下文中也不存在可泄漏的隐私数据。

### 4.4.2　SSE 流式协议

对话走 SSE 流式链路：小程序 → Java `POST /api/ai/chat/stream`（SseEmitter 转发，JWT 解析 userId、2000 字上限、错误只发 code）→ Python `POST /v1/chat/stream`。事件协议定义五类事件：`token`（回复文本增量，逐字下发）、`status`（阶段提示，如"正在为您挑选商品…"，业务取数阶段实时提示但不外显内部术语）、`items`（商品卡片数据，先于回复文本下发）、`done`（结束，含 suggestions 下一轮建议）、`error`（按白名单文案脱敏的错误）。Java 侧透传 `productId`（商详页进线携带）使"这个"具有明确指代对象。

# 5　系统实现

## 5.1　电商核心功能实现

**商品与订单域**：商品模块实现多规格（规格表独立价格库存）、批量上下架、内联快编与商品卡预览；订单模块实现状态机（待付款→待发货→待收货→已完成/已取消/售后中），订单与明细均保存商品快照。订单超时自动取消与优惠券过期由 Spring Schedule 定时任务扫描处理，取消时回滚库存。

**秒杀防超卖**：采用"Redis Lua 原子预扣库存 → 数据库乐观锁落库 → 一人一单约束"三层组合。Lua 脚本将"读取库存—判断—扣减"合并为原子操作，绝大多数无效请求被挡在 Redis 层毫秒级快速失败（返回业务码 50012），不落库、不占连接池；乐观锁兜底极端并发下的数据库一致性。高并发实验（见 6.2 节）验证三档并发下成功订单数均精确等于库存、零超卖、无一人一单突破。

**溯源模块**：管理员维护批次档案（产地、种植户、质检结果、农药残留检测、认证类型与证书图片）与生产记录（播种/施肥/浇水/病虫害防治/采收，含日期与操作人），系统以 ZXing 为每批次生成二维码，消费者扫码查看完整溯源时间线。溯源数据同时是 RAG 知识来源：生产记录与溯源档案按句子边界 180/30 切块入库为 `trace_knowledge` 条目，使"赣南脐橙是怎么种出来的"这类问题可以被检索回答——切块选 180 字符、重叠 30 是因为单条生产记录较短，以句子为边界切块可避免关键事实被拦腰截断（更大粒度的对比实验见 6.9 节，待运行）。

**搜索与评价**：搜索框实现"关键词 + 语义召回"双通道，语义召回命中带高亮，空结果退回 MySQL 全文检索；热词后台可配。评价模块在用户提交后调用 AI 服务 `/v1/sentiment/batch` 做规则情感分析（领域词库 + 否定翻转 + 程度副词 + 评分先验，确定性输出零 LLM 成本），管理端回复后同步回写，商品详情接口聚合返回好评率与好评关键词标签，作为商详页"口碑摘要条"与导购个性化重排的口碑信号来源。

**模拟支付与消息中心**：支付为模拟实现（需求边界明确预留微信支付接口），下单后创建支付单、回调改状态、Redis 记录支付流水；管理员发货与售后处理结果通过站内信（user_message 表，与业务同事务写入）通知用户，首页铃铛展示未读红点。

## 5.2　RAG 检索链路实现

### 5.2.1　三路召回与线性加权融合

检索器（`app/rag/retriever.py`）按三通道并行召回后融合，核心融合逻辑可概括为：

```sql
-- 全文通道（MySQL ngram FULLTEXT，BM25 相关度排序）
select id, question, answer,
       match(question, answer, keywords) against (:q in natural language mode) as relevance
from ai_faq
where status = 1
  and match(question, answer, keywords) against (:q in natural language mode)
order by relevance desc limit 10
```

```python
# 线性加权融合（节选语义）
score = vec + min(keyword_hits, 3) * 0.5 + 0.3 * fulltext_relevance_normalized
# 确认带裁决：商品域条目只凭语义进带 [0.5, 0.6) 且无词面佐证 → 剔除
if (not keyword_hit and not fulltext_hit
        and 0.0 < vec < 0.6 and category in PRODUCT_CATEGORIES):
    continue
```

**为什么弃用 RRF**：实现过程中曾按业界惯例实现 RRF(k=60) 融合，复测当场暴露退化——RRF 按排名融合，会把"两路排名相同"的条目分数压到几乎相等（实测 0.0328 vs 0.0323），向量距离信息丢失；在人工改写集上生产路径 Hit@1 从 90.3% 退到 83.3%，正确条目被"关键词多命中一条"的同分对手挤到第二。线性加权保留分数差异，正确条目得以稳居第一。这一选型结论有存档对比，是"融合策略应与分数分布匹配"的具体例证。

**词面校验的实现**：将查询按停用词表（"推荐/什么时候/多少/怎么/如何"等低区分度通用词）切分为片段，条目 question+answer 原文须包含任一 ≥2 字片段方可保留全文命中。没有这一步，"推荐一部电影"会凭"推荐"二字命中大量含"推荐"的条目，域外问题经全文通道回流——这正是关键词通道当年踩过的坑（关键词通道命中加分因此也做了停用词过滤，停用词命中不加分、也不豁免拒答阈值）。

**通道退场**：全文通道检索异常（索引缺失、库故障）时自动退化为向量+关键词两路，向量库故障时退化为词面两路——检索层永不因单通道故障对用户报错，只以日志告警。

### 5.2.2　交叉编码重排

三路融合的实测画像（见 6.3 节）是"Hit@3 接近满分而 Hit@1 偏低"——正确条目几乎都在召回池里，融合排序排不准第一名。修复这一差距最稳的手段是交叉编码重排。实现上选择 BAAI/bge-reranker-base 的量化 ONNX 导出（266 MB）：onnxruntime 与 tokenizers 均为 fastembed 既有依赖，本地 CPU 推理、零新增依赖、零 LLM 额度，规避了引入 torch 大依赖的问题。重排以"融合序"为保底序（重排分同分时保持原序），失败自动回退融合序；重排只调整**已过闸门条目**的先后、绝不放行新条目，反幻觉语义不变；开启重排时召回深度加深到 20 条再重排截断 Top-5，服务启动时预热模型以消除首查延迟。

### 5.2.3　知识入库与增量索引

知识库内容生产有四条路径，全部汇聚到 `ai_faq`：

1. 管理后台手写 FAQ（保存即增量 upsert 向量索引，停用/删除即时下架，索引同步失败显式提示"需重建"而不静默）；
2. 种子脚本按业务规则生成（36 条平台规则）；
3. 派生脚本为每个在售商品与每个二级类目生成知识条目，溯源数据按 180/30 句子边界切块入库；
4. **管理端文档上传**：运营上传 txt/md/docx/pdf 文档，服务端抽文本（txt/md 直接解码并兼容 gb18030；docx 以标准库 zipfile+XML 抽取段落，不引重依赖；pdf 用 pypdf 逐页抽取）后按 **320/60** 切块——文档块比溯源块更大，因为政策/手册以条款为单位，沿用 180/30 会把"退款时限"这类关键句拆散——每块写入 `ai_faq`（category=doc_knowledge，question 存"标题·第 i 段：块首"锚点以便"依据"标签追溯到出处文档），同名文档重复上传按来源整批先删后入（幂等替换）。

商品索引同步走另一条链路：商品新增/上下架由 Java 异步通知 Python `POST /v1/admin/kb/products/upsert` 增量更新，管理页保留全量重建按钮兜底；索引状态页以"启用条数 / FAQ 索引条数 / 商品索引条数 / 在售商品数"四数并列，不一致即告警。

### 5.2.4　依据引用与结构化下发

知识问答命中的条目以 `references`（id+问句）结构化随响应下发，前端在气泡下方渲染"依据"标签。设计考量是：引用若由模型复述必然漂移，"拼不出来的话才说不出错"——引用列表由服务端按检索命中直接拼装，不经模型转手，使反幻觉具备可核对的证据链；同一轮多工具多步取到的引用去重合并，上限 4 条。

## 5.3　智能体编排实现

### 5.3.1　工具目录与调用契约

6 个能力注册为 function schema（`app/agent/tool_defs.py`），schema 描述即调用契约的一部分：`product_search` 的 `query` 参数描述明确要求"把用户真实需求补全成一句完整的话"（如"便宜点的"结合上文写成"50 元以内的柑橘"）；`inDomain` 设为**必填**，描述写明"必须给出判断，省略等于放弃拒答的机会"——这是实测教训的固化：该字段原为可选，模型经常省略，而执行器"没有经营域判定时不拒答"的保守阀会让域外请求落到热销兜底并端出商品卡（探针"帮我写一首关于秋天的诗"曾泄漏 1 张卡），将其提为必填后域外探针泄漏降为 0/8 且域内泛推荐 6/6 未误拒。`escalate_human` 的 `reason` 必填，用于工单与管理端日志。

### 5.3.2　有界 ReAct 循环

agent 节点的循环骨架如下（伪代码）：

```python
demands = count_demands(question) if looks_multi_demand(question) else 1
for step in range(AGENT_MAX_STEPS):          # 步数上限 = 2
    if calls >= AGENT_MAX_TOOL_CALLS: break  # 调用数上限 = 4
    if step > 0 and demands > calls:         # 补齐核对轮提示
        inject_system("用户消息约含 N 个诉求，请逐个核对补调")
    resp = planner.invoke(messages)          # bind_tools 规划
    for tc in resp.tool_calls:               # 一轮可并行多个
        key = (tc.name, canonical_json(tc.args))
        if key in seen:                      # (工具,参数) 去重
            backfill("该查询已执行过"); break
        obs = run_tool(ctx, state, tc.name, tc.args)
        messages.append(feedback(obs))       # 只回灌"够不够用"摘要
    if all(o.status in ("ok", "refused", "need_login") for o in step_obs) \
            and not (demands > 1 and calls < demands):
        break                                # 资料够 → 提前退出
```

四项有界机制各有实测依据：**步数上限 2**——免费网关单次规划 6~15 s，不封顶则最坏情况延迟与额度不可控；**调用数上限 4**——防止一条消息打满免费额度；**去重**——实测模型把工具结果喂回去后可能不收敛（再发同样的调用），去重让它"原地打转"时不重复取数不重复烧额度；**提前退出**——本步资料全部可用或已落到确定性出口（域外拒答、未登录）时再问一次模型只会白烧一次往返。空结果（empty/error）是唯一允许走反思重试的情形，此时观察摘要带提示"可换检索表述或品类词重试一次，否则如实说明"。

回灌给规划器的观察摘要刻意只含"够不够用"的信号（工具名、状态、条数/字符数、提示），不把大段资料原文喂回——规划器不需要读资料（作答由 generate 节点看完整观察），少喂既省 token 也更有利于收敛。

### 5.3.3　五级证据链导购执行器

所有"把关"逻辑集中在工具执行器（`app/agent/executors.py`）一处实现，不放提示词、也不放图结构——因为它们是量化实验实测出来的结论，重构只改"谁决定调用什么"，不改"调用之后怎么把关"。`exec_product_search` 按 0→5 级执行（见 4.2.3 节），统一出口 `_ok()` 完成"证据序 → 个性化重排 → LIKE 命中置顶 → 截断卡片上限（4 张）→ 口碑注句 → payload 与卡片同源"的流水线。**payload 与 items 必须同源**：否则大模型讲的是前两款、用户点的卡片是另外几款。卡片截断为 4 张源于端到端实测——语义召回整批回传时聊天气泡下一次冒出 8 张卡还混进无关品，用户不会往下翻，"少而准"优于"看起来给得多"。

**域外拒答与安全阀的平衡**：`inDomain=false` 且两路皆空才拒答；品类词 LIKE 有命中即推荐（"库里确实在卖"是正面证据，优先于模型的域判断，宁可少拒不误伤）；未拿到判定（模型故障走兜底）时不拒答，故障期行为与改造前完全一致。这一保守设计使闸门本身不成为新的故障源。

### 5.3.4　生成节点与确定性出口

generate 节点按确定性优先级检查：转人工话术 → 域外拒答 → 未登录引导 → 商品事实问答 → 取数故障降级 → 知识库未覆盖拒答，五类不经大模型的出口保证了最坏情况下的输出确定性与零额度成本。只有 `status=ok` 的观察才允许进入生成上下文——error 的 payload 一律为空（异常细节只进日志），否则内网地址、集合名等内部字样有概率被模型复述给用户。智能体一个工具都没调时（礼貌回应/纯追问）走引导式回复而非"知识库未覆盖"拒答——根本没查过，拒得不成立。

### 5.3.5　降级阶梯

故障不是例外而是常态假设，系统实现四级降级：① 上游模型不支持 function calling 或 bind_tools 初始化失败 → 退回"规则分类 + 单工具"路径（`classify_full`：高置信规则 → LLM 分类 → 关键词兜底三级，永不自行抛异常），功能不回退只降速，并打 WARNING 防止"以为在跑智能体、实际一直在跑降级"的静默退化；② 规划调用抛异常（429/超时）→ 同上退化为单工具取证；③ 生成调用失败 → 固定降级话术（含客服电话），不白屏；④ 免费额度故障时评测脚本自动识别（统计 LLM 失败数与 429 次数，有最终失败即标记存档无效并以非零码退出），保证评测数据不被限流污染。客户端内置退避重试（max_retries=2，429/5xx 自动退避）。

### 5.3.6　口碑话术的服务端模板化

端到端实测发现模型在引用商品口碑时存在"语义级越界"：`reviewCount=3、positiveRate=66.67` 被说成"口碑不错"，评价文本中的"回购"关键词被说成"回购率"，销量 1046 被说成"1046 人回购"。提示词约束（禁句清单 + 断言）能压住具体禁句但压不住同义改写。最终按确定性思路收口：口碑那一句由服务端模板拼装——`reputation_text()` 按 reviewCount/positiveRate/topKeywords 产出"3 条买家评价，好评率 66.7%，买家提到：新鲜、多汁"，零评价/字段缺失/脏字段一律输出"暂无评价数据"；句子写入商品卡 `reputation` 字段、与作答上下文同源下发，提示词只允许**一字不改地引用**这一句（禁令同时保留作第二道约束）。思路是"把没有依据的话变成拼不出来的话"，而不是指望模型自律。该结论的适用边界也如实记录：被模板绑定的只有口碑一句，模型自行组织的其余话术仍是概率性生成，故系统口径是"口碑宣称已模板化、数值与指标名同源"，而非"杜绝虚假宣传"。

## 5.4　智能导购与多入口实现

**多入口进线**：AI 导购能力面向用户有多个入口——首页悬浮球、订单页、售后页（携带订单上下文）与商品详情页（携带 productId）；商详页进线时聊天页顶部显示"正在咨询的商品"且可清除。带上下文进线使"这个能放多久？怎么保存"有了明确指代，由第 0 级商详指代通路承接。

**商品卡先行下发**：导购结果以 `items` 事件独立下发，卡片先于回复文本到达——取证阶段完成（实测 P50 约 2.2 s）即可渲染卡片，大模型组织文字的 8~10 s 被用户感知为"已经在挑了"，显著缩短主观等待。

**个性化信号采集**：订单/收藏/加购/评价四路信号直接来自业务表；浏览行为由前端 `POST /api/product/view` 上报（7 天窗口、3 天半衰期指数衰减）；搜索词由搜索接口尽力落库（失败只丢一条信号不报错），关键词经 LIKE 在售商品名映射到品类。游客不叠加偏好项，其余信号仍生效。

## 5.5　运营闭环实现

AI 能力的长期可用依赖运营闭环，系统实现了三块：

1. **知识库维护**：管理后台知识库页（经 Java 代理、仅管理员可写）承担 FAQ 增删改查、启停、两个索引的全量重建、文档上传入库、近 7 日被 AI 引用的知识 Top（kb_hit_log 聚合）与 AI 运营统计（近 7 日对话轮数、拒答率、工具调用分布）——"运营改一条知识 → 索引即时生效 → 客服当场答对"闭环。
2. **对话审计**：每轮对话（问题、回复、工具调用序列、命中知识条目）落库 `ai_chat_log`，管理页可查，是运营统计与问题排查的依据。
3. **AI 运行配置**：检索条数、闸门阈值、重排开关、编排步数/调用上限等以 `sys_config` 的 `ai_*` 键承载，管理页可调，运行时以 60 s TTL 缓存读取——调参不需重启即生效；同时显式传参（单测/实验脚本）优先级最高，便于实验复现。转人工工单在管理端完成"待处理 → 已处理"原子抢占（防双管理员重复处理），处理结果计入导航栏待办徽标。

## 6.2　实验一：秒杀高并发压测

**方案**：`SeckillConcurrencyTest` 以真实 MySQL + Redis 起测，CountDownLatch 同时放行，三档并发（服务层 100 并发抢 50 库存、服务层 500 并发抢 180 库存的放大档、HTTP 接口层 100 并发抢 50 库存），校验防超卖与一致性。数据如表 6-2 所示（2026-10-17 复测，3/3 通过）。

**表 6-2　秒杀压测结果（存档：target/surefire-reports，复现命令见量化实验报告 §9）**

| 档位 | 总请求 | 成功订单 | 售罄拒绝 | 系统错误 | 墙钟耗时 | QPS | 防超卖 |
|---|---|---|---|---|---|---|---|

0.35 阈值下的泄漏结果荒谬到可读（可作反例佐证闸门必要性）：手机壳→带壳毛豆（0.453）、口红→丹东红颜草莓（0.460）、跑步鞋→金华火腿（0.392）、笔记本电脑→烟台红富士苹果（0.355）。根因有三：阈值场景错位（0.35 是为有全文检索可退的搜索框定的）、导购分支没有拒答出口、意图判成 recommend 后链路上再无人质疑。修复后按曲线选点 0.47 并新增确定性拒答出口，复测域外泄漏率 60% → 0%，域内召回率 100% → 90%（剩余 10% 弱命中域内请求由品类词 LIKE 接住，端到端实测正常出推荐）。**端到端复核**："推荐一双跑步鞋"返回确定性拒答且回复不含任何商品名；"有什么水果推荐"正常返回三款带价格/产地/销量的推荐——修复没有误伤正常导购。

## 6.7　实验六：智能导购召回与个性化

**方案**：40 条人工导购问句覆盖全部主营类目，每条标注可接受的二级类目集合（单一 gold，同类目内任意商品计命中，跨类目合理替代不计分——口径偏保守）；在售商品池 202 件；三通道同池对比，指标 Hit@1 / Hit@5 / P@5 / MRR / 类目覆盖。结果如表 6-10 所示（存档：`recommend_eval.json`）。

**表 6-10　导购召回三通道对比（40 条问句 × 202 件在售商品）**

| 通道 | Hit@1 | Hit@5 | P@5 | MRR | 类目覆盖 |
|---|---|---|---|---|---|
| 热销榜 | 7.5% | 15.0% | 5.0% | 0.101 | 10/40 |
| 关键词 LIKE | 60.0% | 75.0% | 26.5% | 0.667 | 36 |
| **语义向量** | **77.5%** | **92.5%** | **52.0%** | **0.842** | **40** |

语义通道相对关键词的增益可归因于"用户说场景不说品类"的问法——"过年走亲戚拎点什么体面""给小宝宝做辅食买什么"抽不出词面匹配。类目覆盖 40/40 说明 202 件商品索引无类目盲区。剩余 3 条未命中样本（"浆果都有什么""有什么泡水喝的"）共同特征是期望跨多个二级类目的聚合召回，向量通道按整体相似度排序、未做类目多样化，改进方向为类目配额打散或 MMR。

**个性化对照重放**（性质为机制验证，非效果评估）：对每条问句取语义召回 top-8 中"相关但排在 4~8 名"的商品为目标，合成近期连购 3 件同类目的用户历史，同一份候选分别经"无偏好/有偏好"重排。结果：目标商品进 top-5 比例 0.0% → 95.0%，平均名次提升 +2.15 名。必须如实标注：基线 0.0% 是构造使然（目标即按"基线落在 top-5 之外"筛选），判定类目又是被优化的信号本身，故该实验证明的是"重排公式能把偏好类目商品推入前五"这一机制，**不能证明个性化对用户的实际价值**——后者需要 A/B 或线上点击率数据，本系统未采集。

## 6.8　实验七：智能体工具编排

**方案与口径**：hold-out 集每条已标意图映射到期望工具（faq→kb_search、recommend→product_search、order→order_query、logistics→logistics_query、after_sales→after_sales_query、human→escalate_human、smalltalk→不调用任何工具），命中定义为"期望工具在实调集合里"（允许并行多调；规则前置短路的 human/smalltalk 记命中——把省掉的调用记成错误等于惩罚优化）。工具执行用桩（检索/商品向量召回/LLM 全部真实），测的是"选什么工具"而非"取数对不对"，后者由 Java 单测与端到端复核负责。

**结果**（存档：`agent_eval_plan_holdout.json`、`agent_eval_plan_holdout_prefix.json`）：两次独立测量工具选择准确率同分 **94/109 = 86.2%**（lexical 93.8% / semantic 83.1%），规划调用 121 次，取证延迟 P50 2 249 ms / 均值 7 529 ms / P95 27 850 ms（长尾由免费档上游排队主导，引用时应同时给 P50 与调用次数这一结构量）。最有价值的是与规则通道的对照：同一批题、同一套标注，规则通道语义子集 23.4%、全集 37.6%，而 function calling 编排 semantic 子集 83.1%、全集 86.2%——把"规则不能当语义分类器"的批评变成了替换证据：不是把规则改得更聪明，而是换了一层能读懂句子的决策者。分意图命中率：recommend 100%、after_sales 93.3%、order 86.7%、human 85.7%、faq 85.0%、smalltalk 78.6%、logistics 73.3%（最弱一类，误判方向是"派送环节的事实分散在订单/物流/售后三个接口"，模型选了最近的一个，属边界样例不足）。

**缺陷修复与新集复测**：① 规划提示词只写了"要事实必须调工具"没写反面，14 条纯寒暄 6 条被硬塞 kb_search（smalltalk 57.1%）；补"无事实需求一律不调用工具"规则后，用**未参与任何调试、与 hold-out 零重合**的定向新集复测（`agent_probe_overcall.json`，12 条寒暄 + 8 条业务对照）：总体 18/20 = 90.0%，寒暄不调用工具 10/12 = 83.3%——修订后成绩只引用零重合新集，hold-out 同类复测仅作行为回归（观测→改→同集复测即二次泄漏）。② 商详页指代句的卡片被语义召回"抢走"（"这个能放多久"top-1 0.518、8 张卡首张是金针菇，与真品类问句 0.558 分数重叠），判据从"分数"换成"结构"（第 0 级商详指代通路），4 条回归测试钉住。③ `inDomain` 可选导致域外泄漏 1/5，提为 schema 必填后新写域外集 0/8 泄漏、域外探针回归 0/5、域内泛推荐保护集 6/6 未误拒。

**端到端复核**（真实 Java + 真实索引 + 真实模型）：「这个能放多久？怎么保存」按商品事实答"常温避光、保质期 30 天"没有编造；「怎么申请退款？另外有没有 50 元以内的橙子」一次回复两个诉求（kb_search + product_search 并行，5 张卡含三款 ≤50 元柑橘逐条给价格/产地/销量）——这是旧单分支架构做不到的。**多诉求覆盖边界**：3 条 multi_intent 探针 2 条同时命中两个工具、1 条只调了一个（少答一半），编排层以"诉求确定性计数 + 补齐核对轮"缓解但未做模型级硬保证，论文口径为"支持一句多诉求并行取证（实测 2/3 探针命中两个工具）"，不能写成"已保证"。

## 6.10　测试结论

综合功能测试与八项实验：① 交易侧正确性结论稳固——三档高并发秒杀零超卖、状态机与资金口径一致；② RAG 检索链路达到主口径 Hit@1 97.2% / Hit@3 100% / MRR 0.986，域外拒答 100% 且域内零误拒，反幻觉目标达成；③ 智能体编排相对规则路由在语义子集上提升约 60 个百分点，一句多诉求并行取证为真实新增能力，代价（延迟、额度）被有界机制封顶；④ 导购语义召回显著优于关键词通道（Hit@1 +17.5 个百分点、P@5 +25.5 个百分点），个性化重排机制得到验证但线上效果待 A/B；⑤ 延迟优化轨迹证明串行 LLM 调用次数是首 token 延迟的主导结构量，规则前置与调用合并分别把寒暄与导购分支缩短 5.1 s 与 8.8 s。

# 7　总结与展望

## 7.1　工作总结

本文面向农产品电商的智能导购需求，设计并实现了一个基于 RAG 与大模型智能体的三端一体系统，主要完成：① 完整的电商交易闭环（含高并发秒杀防超卖、溯源、评价口碑聚合）；② 以三路混合召回、线性加权融合、交叉编码重排与"阈值 + 确认带 + 词面校验"双道闸门构成的反幻觉 RAG 检索链路；③ 基于 LangGraph 与 function calling 的有界工具编排智能体，规划-执行-作答三节点分离，五类确定性出口覆盖最坏情况；④ 五级证据链导购与三入口共用口径的六路信号个性化重排；⑤ 覆盖知识维护、对话审计、运行配置与转人工工单的运营闭环；⑥ 与存档同源的八项量化实验。实验表明：检索主口径 Hit@1 97.2%、MRR 0.986，域外拒答率 100%（域内零误拒），智能体工具选择准确率 86.2%（同批规则通道 37.6%），秒杀三档并发零超卖，导购语义召回 Hit@1 77.5%。系统验证了在免费大模型网关、本地推理、单机部署的低成本约束下，RAG 与智能体技术在垂直电商场景的工程可行性。

方法论层面，本文的两条实践结论具有一般参考价值：其一，评测集与调参集必须隔离——规则通道"96.1%"与"37.6%"的巨大落差说明未经泄漏控制的能力读数不可信，few-shot 例句取自评测样本属于同类错误；其二，重构不应破坏已实测的闸门——架构从意图路由改造为工具编排时，全部把关逻辑收敛到执行器唯一实现，"改决策者、不改把关者"使量化结论在重构后持续成立。

## 7.2　不足与展望

系统的不足与后续改进方向包括：

1. **生成质量评估待补全**：忠实度评估、切分策略对比与步数消融三项实验脚本已就绪但待运行（见 6.9 节），回填数据后方可完整刻画生成层质量与有界编排的取舍曲线。
2. **个性化效果未经线上验证**：个性化重放是机制验证，真实价值需 A/B 实验或点击率数据支撑；建议后续埋点采集导购卡片点击行为。
3. **检索改进项**：高频 FAQ 补同义问法库或多向量索引（唯一人工层未命中样本为跨域等价改写）；导购候选按类目配额打散或 MMR（3 条跨类目聚合未命中）；知识库扩容后阈值需在分布上重选而非固定 0.5。
4. **多意图覆盖的硬保证**：编排层确定性核对已显著缓解，但若要求模型级保证需增加一次核对往返（+6~15 s），可在响应延迟与覆盖完整性间做可配置权衡。
5. **工程方向**：意图分类可换 fine-tuned BERT 分类头从秒级压到毫秒级（同时改善全部分支）；秒杀扣减可异步落库并以 Redis 对账；支付与物流对接真实服务；AI 运营看板补充时序图表。
6. **边界如实声明**：支付与物流为模拟实现；"口碑宣称已模板化"不等于"杜绝虚假宣传"，模型自由话术仍属概率性输出；LLM 指标受免费档服务质量波动影响，跨环境复测数值会浮动。
