## 1. 背景与目标

### 1.1 背景

当前系统仅支持基于 MySQL `LIKE` 的商品关键词匹配，检索能力薄弱，与"农产品直供 + 溯源信任"的产品定位不匹配。需求文档（§4.9）明确要求搜索功能包含：关键词搜索、搜索结果（图/名/价/销量）、热门搜索词、搜索历史、排序筛选。

### 1.2 目标

- 关键词搜索具备**相关性排序**（不再按创建时间粗暴倒序），返回商品图、名称、价格、销量
- 搜索结果**关键词高亮**，用户能直观看到命中位置
- 支持**热门搜索词**（自动统计 + 管理端手工配置）
- 支持**搜索历史**（小程序本地存储）
- 与现有分类浏览、排序筛选（hot/new/price_asc/price_desc）兼容
- **零新增组件**：不引入搜索引擎中间件，复用现有 MySQL 能力

### 1.3 非目标（本期明确不做）

- 语义搜索、拼音纠错、同义词扩展（引擎不支持，见 §11 扩展路径）
- 全局站内搜索（订单/用户/评价不纳入检索）
- 搜索日志审计与分析看板

## 2. 现状分析与问题

### 2.1 现有实现

用户端商品查询入口统一为 `ProductController#listProducts`（`GET /api/product/list`），核心逻辑在 `ProductServiceImpl#buildUserQueryWrapper`：

```java
if (StrUtil.isNotBlank(request.getKeyword())) {
    wrapper.and(w -> w.like(Product::getName, request.getKeyword())
            .or().like(Product::getSubtitle, request.getKeyword()));
}
```

关键词仅匹配 `name`、`subtitle` 两个字段，排序默认走 `sort + create_time`。

### 2.2 问题清单

| 问题 | 现状表现 | 影响 |
|---|---|---|
| 无相关性排序 | 命中"脐橙"的结果按上架时间排，与关键词匹配度无关 | 用户找不到想买的商品 |
| 匹配字段少 | 不含分类名、产地 | 搜"江西"、"水果"无结果 |
| 无高亮 | 结果列表无法看出命中位置 | 检索体验差 |
| 无热词 | 首页无热门搜索引导 | 流量分发能力缺失 |
| LIKE 性能 | `%keyword%` 无法走索引，全表扫描 O(n) | 数据量增大后线性劣化 |

## 3. 技术选型

### 3.1 备选方案对比（2026-09-13 核实）

| 对比项 | 方案A：MySQL LIKE（现状） | **方案B：MySQL FULLTEXT（ngram）** | 方案C：Meilisearch | 方案D：Elasticsearch |
|---|---|---|---|---|
| 新增部署成本 | 无 | **无（MySQL 8.4 内置 parser）** | 一个 Docker 容器 | 集群/大内存 |
| 新增内存 | 0 | **0** | ~100~500MB | 2GB+ 起步 |
| 中文支持 | 无 | **内置 ngram（默认 bigram）** | 内置 CJK 分词 | 需装 IK 插件 |
| 相关性排序 | 无 | **有（词频/位置相关度分数）** | 强 | 最强 |
| 数据一致性 | — | **天然一致（直查业务表）** | 需索引同步 | 需同步/CDC |
| 高亮 | 需手写 | **需应用层手写（无原生）** | 原生 `_formatted` | 支持 |
| Typo 容错 | 无 | 无 | 有 | 有 |
| 自带管理界面 | 无 | 无 | 有 Web UI | 需 Kibana |
| 单字搜索 | 支持 | **受限（bigram 下需降级）** | 支持 | 支持 |
| 运维成本 | 无 | **无** | 低 | 高 |

### 3.2 选型结论：MySQL FULLTEXT（ngram）

理由：

1. **零新增组件**：MySQL 8.4（当前 docker-compose 已用 `mysql:8.4`）内置 ngram 全文解析器，无需装插件、无需新容器、无需额外内存。部署形态不变。
2. **数据天然一致**：直接查业务表，商品增删改后搜索结果**即时正确**，没有"索引同步失败导致搜索结果陈旧"的问题——这是相对专用搜索引擎最大的工程简化。
3. **毕设规模性能足够**：MySQL 全文索引走倒排索引，`MATCH ... AGAINST` 实测 100 万行约 50ms 级；本项目商品表个位数~千级，延迟与 LIKE 相当或更优，且**不随数据量线性劣化**。
4. **相关性排序开箱即用**：`MATCH AGAINST` 返回相关度分数（词频、词位置、文档长度归一化），按分数倒序即完成需求文档要求的"相关性排序"，无需手写打分。
5. **实现简单可讲**：SQL 层面一个 `FULLTEXT INDEX` + `MATCH AGAINST`，答辩讲解成本远低于引入搜索引擎，且能讲清楚"倒排索引/ngram 分词"原理。
6. **后续可平滑升级**：接口与热词设计不依赖具体引擎，若未来数据量上量，可无缝切换到 Meilisearch/ES（见 §11），前端与接口不变。

**取舍（如实说明）**：

- 无 Typo 容错、无拼音/同义词——毕设场景不构成短板，但答辩表述中不要声称具备
- 高亮需应用层实现（§7.4 提供工具类）
- bigram 下**单字搜索命中受限**，需要降级策略（§7.2）
- 中文分词是"字粒度 n-gram"，无语义分词（"脐橙"能命中，但词边界理解弱于 IK/jieba）

### 3.3 版本说明

| 组件 | 版本 | 说明 |
|---|---|---|
| MySQL Server | 8.4（现有） | ngram parser 为内置服务插件，自动加载，无需安装 |
| ngram_token_size | 2（默认） | bigram；只读变量，启动时配置；对中文商品名场景默认值即可，一般无需修改 |
| Spring Boot / MyBatis-Plus | 4.1.1 / 3.5.15（现有） | Mapper 支持 `MATCH AGAINST` 原生 SQL，无特殊依赖 |

> ngram 相关官方行为（MySQL 8.4 Reference Manual §14.9.8）：
> - 建索引：`WITH PARSER ngram`
> - 自然语言模式：搜索词转为 ngram **并集**（宽松召回）
> - 布尔模式：搜索词转为 ngram **短语**（精确匹配）
> - `innodb_ft_min_token_size` 等词长配置对 ngram **无效**，无需设置
> - 默认英文停用词表对纯中文 token 无影响；无需配置停用词

### 4.1 架构图

```
┌─────────────────────────────┐
│         小程序端              │
│  搜索页(历史/热词/结果/高亮)   │

│         Spring Boot          │
│  ┌────────────────────────┐  │

│  ├────────────────────────┤  │
│  │ SearchService           │  │  ← 关键词非空走此链路
│  │  ├─ FULLTEXT 查询组装    │  │
│  │  ├─ 高亮工具（应用层）    │  │
│  │  └─ 单字降级 LIKE 策略   │  │
│  ├────────────────────────┤  │
│  │ HotWordService          │  │  ← 热词统计/查询
│  └────────────────────────┘  │

       │          │          │
  ┌────▼─────────┐ │    ┌────▼────────┐
  │ MySQL         │ │    │ Redis        │
  │ 商品表+ngram  │ │    │ 热词计数     │
  │ FULLTEXT索引  │ │    │ (可选优化)   │
  │ 热词表        │ │    │             │
  └──────────────┘ └────┴─────────────┘
```

### 4.2 查询路由策略

| 场景 | 数据源 | 说明 |
|---|---|---|
| `keyword` 非空 且 长度 ≥ 2 | **MySQL FULLTEXT**（`MATCH AGAINST` 自然语言模式） | 相关性排序 |
| `keyword` 为单字符 | **MySQL LIKE 降级** | bigram 下单字命中受限（§7.2） |
| `keyword` 为空（分类浏览/热销/新品/首页） | MySQL 普通查询（现状不动） | 不引入无意义开销 |
| 管理端商品列表 | MySQL 普通查询（现状不动） | 后台检索不纳入搜索模块 |

### 4.3 数据一致性

**无同步机制**：FULLTEXT 索引由 InnoDB 在业务表 `INSERT/UPDATE/DELETE` 时自动维护，搜索永远读到最新数据。商品上下架后通过 `WHERE status = 1` 实时过滤。此方案**不存在**"索引陈旧"问题，删除 §4.3 的同步策略设计（相对 v1.0 的最大简化）。

## 5. 数据模型设计

### 5.1 新增表：搜索热词表 `search_hot_word`

```sql
CREATE TABLE IF NOT EXISTS `search_hot_word` (
    `id`           BIGINT      NOT NULL AUTO_INCREMENT COMMENT '主键',
    `word`         VARCHAR(50) NOT NULL COMMENT '搜索词',
    `search_count` INT         NOT NULL DEFAULT 0 COMMENT '累计搜索次数',
    `sort`         INT         NOT NULL DEFAULT 0 COMMENT '排序值，越大越前',
    `status`       TINYINT     NOT NULL DEFAULT 1 COMMENT '0=隐藏 1=展示',
    `is_manual`    TINYINT     NOT NULL DEFAULT 0 COMMENT '0=自动统计 1=管理员手工配置',
    `create_time`  DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    `update_time`  DATETIME    DEFAULT NULL ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_word` (`word`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='搜索热词表';
```

### 5.2 商品表新增 ngram 全文索引

在现有 `product` 表上新增（不重建表，`ALTER TABLE` 即可）：

```sql
ALTER TABLE `product`
    ADD FULLTEXT INDEX `ft_product_name_subtitle` (`name`, `subtitle`) WITH PARSER ngram;
```

**索引设计说明**：

| 项 | 值 | 说明 |
|---|---|---|
| 索引列 | `name` + `subtitle` | 与现有 LIKE 匹配范围一致；后续如需支持"产地"检索可加 `origin` 列（需重新建索引） |
| 解析器 | `WITH PARSER ngram` | 中文支持的关键；默认 bigram（`ngram_token_size=2`） |
| 词长配置 | 不配置 | `innodb_ft_min_token_size` 等对 ngram 无效（官方文档明确） |
| 停用词 | 不配置 | 默认英文停用词表不影响纯中文 token |

**注意**：FULLTEXT 索引创建耗时与表大小相关，当前表仅个位数行，秒级完成；执行前无需锁表担忧（演示规模）。

### 5.3 落地脚本

新增 `sql/search_module.sql`，内容为 §5.1 建表 + §5.2 建索引两条语句，与现有 `fix_category_ids.sql` 等模块脚本同目录管理。

## 7. 核心实现要点

### 7.1 新增依赖

**无需新增任何 Maven 依赖**（相对 v1.0 移除 meilisearch-java）。全部基于 MyBatis-Plus 现有能力。

### 7.2 搜索 SQL（核心）

新增 Mapper XML：`resources/mapper/ProductSearchMapper.xml`（或直接在 `ProductMapper` 增加方法）：

```xml
<!-- 相关性排序搜索：自然语言模式，宽召回 -->
<select id="searchByFulltext" resultType="com.lichun.agsell.model.entity.Product">
    SELECT id, name, subtitle, category_id, price, original_price,
           stock, sales, main_image, origin, sort, status, create_time,
           MATCH(name, subtitle) AGAINST (#{keyword} IN NATURAL LANGUAGE MODE) AS ft_score
    FROM product
    WHERE deleted = 0
      AND status = 1
      <if test="categoryId != null">
        AND category_id = #{categoryId}
      </if>
      AND MATCH(name, subtitle) AGAINST (#{keyword} IN NATURAL LANGUAGE MODE)
    ORDER BY ft_score DESC
    LIMIT #{offset}, #{pageSize}
</select>

<!-- 总数（分页用，注意 MATCH 需与索引列一致） -->
<select id="countByFulltext" resultType="long">
    SELECT COUNT(*)
    FROM product
    WHERE deleted = 0
      AND status = 1
      <if test="categoryId != null">
        AND category_id = #{categoryId}
      </if>
      AND MATCH(name, subtitle) AGAINST (#{keyword} IN NATURAL LANGUAGE MODE)
</select>
```

**SQL 关键点**：

1. **`MATCH` 必须写两遍**：MySQL 语法不允许在 `WHERE` 中引用 `SELECT` 列的别名，`ft_score` 排序必须在 `SELECT` 中重新计算
2. **`MATCH` 列必须与索引完全一致**：索引建在 `(name, subtitle)`，查询必须写 `MATCH(name, subtitle)`，否则报错 `Can't find FULLTEXT index matching the column list`
3. **自然语言模式**：搜索词 "脐橙" 转为 bigram "脐橙"（并集），"赣南脐橙" 可命中包含 "脐橙" 的商品；对"水果"这种词命中 `subtitle` 或 `name` 中的分词结果
4. **`deleted = 0`**：与 MyBatis-Plus 逻辑删除口径一致（实体 `@TableLogic` 自动拼接，XML 手写 SQL 需显式带出）

**排序映射**（`sortBy` → ORDER BY）：

| sortBy | ORDER BY | 说明 |
|---|---|---|
| 空（相关度） | `ft_score DESC` | 词频/位置相关度 |
| `hot` | `sales DESC` | 保持与现有口径一致 |
| `new` | `create_time DESC` | |
| `price_asc` | `price ASC` | |
| `price_desc` | `price DESC` | |

> 非相关度排序时，`MATCH AGAINST` 仅作为过滤条件（`WHERE`），排序走业务字段；此时同样命中全文索引加速过滤。

**单字符降级**（`keyword.length() < 2` 时）：

```java
// bigram 索引下单个中文字符无法可靠命中，降级为 LIKE（数据量小无压力）
wrapper.and(w -> w.like(Product::getName, keyword)
        .or().like(Product::getSubtitle, keyword));
```

### 7.4 高亮工具（应用层实现）

```java
/**
 * 关键词高亮：将 text 中出现的 keyword 包裹为 <em> 标签。
 * 逐次 indexOf 定位（非正则），规避用户输入注入正则的风险；keyword 含空格时按词拆分处理。
 */
public static String highlight(String text, String keyword) {
    if (StrUtil.isBlank(text) || StrUtil.isBlank(keyword)) {
        return text;
    }
    String escaped = keyword.trim().replace("<", "&lt;").replace(">", "&gt;");
    // 拆分多词（如"赣南 脐橙"），逐词标记
    String[] words = escaped.split("\\s+");
    StringBuilder sb = new StringBuilder(text);
    // 从后往前替换，避免索引偏移
    for (String word : words) {
        if (word.isEmpty()) continue;
        int idx;
        int from = 0;
        while ((idx = sb.indexOf(word, from)) >= 0) {
            sb.replace(idx, idx + word.length(), "<em>" + word + "</em>");
            from = idx + word.length() + 9; // 跳过已插入标签
        }
    }
    return sb.toString();
}
```

> 说明：应用层高亮为"字符串标记"，非分词级高亮——命中片段与全文索引召回结果可能略有出入（如多词搜索），演示场景可接受。前端对 `<em>` 统一渲染品牌绿加粗。

### 7.5 热词统计策略

| 方案 | 实现 | 适用 |
|---|---|---|
| **方案一（默认，推荐）** | 搜索时 `INSERT ... ON DUPLICATE KEY UPDATE search_count = search_count + 1` | 数据量小，简单可靠 |
| 方案二（可选优化） | Redis `INCR hot:word:{word}` + 定时任务每小时回写 DB | 并发量大时降低 DB 写压力 |

自动词默认 `sort = 0`，按 `search_count` 排序；管理端可手工调整自动词的展示排序与状态。

### 9.3 ngram_token_size（一般无需改）

- 默认 `2`（bigram）满足"赣南脐橙→脐橙"这类中文商品名检索
- 如需支持单字精确搜索，可启动参数 `--ngram_token_size=1`（索引更大、搜索更快但召回更宽）；**改动需重建 FULLTEXT 索引**，且为只读变量须改容器启动命令——毕设场景不建议动
- 配置文件中写法：`[mysqld] ngram_token_size=2`

### 9.4 资源占用

| 项 | 估算 |
|---|---|
| 新增内存 | 0（ngram 索引内存占用纳入 InnoDB 缓冲池，当前表规模可忽略） |
| 新增磁盘 | 全文索引约为被索引文本的 1~2 倍，当前 `name+subtitle` 数据 < 1MB |
| 新增端口/容器 | 无 |

## 11. 风险与后续扩展

### 11.1 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| ngram 分词边界（如 4 字词切分为多个 bigram，召回偏宽） | 少量不相关结果进入列表 | 相关度排序已将精确短语排在前面；可接受 |
| 单字搜索命中受限 | 单字检索效果差 | §7.2 降级 LIKE；产品上引导用户输入 ≥ 2 字 |
| 英文/数字混合词被默认英文停用词影响 | 极少数含英文商品名（如 "Organic"）检索偏差 | 影响极小；确需处理可自定义停用词表（官方 §14.9.4） |
| FULLTEXT 索引与 LIKE 混用导致查询计划异常 | 个别场景走错索引 | 验收清单含 `EXPLAIN` 检查项 |

### 11.2 后续扩展

1. **平滑升级专用引擎**：本方案接口（`/product/search`）、热词表、前端均不绑定 MySQL 实现。若未来商品量上十万级或需 Typo 容错/语义搜索，可替换为 Meilisearch/ES，仅改动 `SearchService` 实现层，接口与前端零改动。
2. **搜索联想（suggest）**：基于热词表 + `keyword LIKE '前缀%'`（可走索引）实现输入即提示。
3. **搜索数据分析**：热词表已沉淀 `search_count`，可扩展按日分区统计，为运营（如新品上架选词）提供依据。
4. **AI 语义搜索（远期）**：结合上一轮 AI 方向分析，可在接口层增加"意图理解"（LLM 改写查询词）后再走 FULLTEXT，无需更换存储。
